# 审批中台拆分指导

## 目标架构

审批能力以独立仓库、独立服务和独立数据库为最终形态：

```text
审批中台
  ├─ 流程定义、版本与发布
  ├─ 条件匹配、节点流转、会签与或签
  ├─ 审批实例、任务、待办与审计记录
  ├─ 组织身份提供方适配
  └─ 结果事件投递与重试

业务项目
  ├─ 业务对象、数据快照和字段语义
  ├─ 提交审批与撤回入口
  ├─ 审批结果事件幂等消费
  └─ 审批通过后的本地事务和下游业务
```

审批中台不得直接访问业务项目数据库，也不得理解销售订单、采购订单、库存或结算等业务规则。

## 当前过渡结构

当前仓库先保留 `xbb-erp-module-approval-contract`，仅放稳定 Java 契约：

```text
ApprovalPlatformApi       业务项目调用审批平台
ApprovalResultHandler     业务项目处理审批结束事件
ApprovalSubmitCommand     冻结业务快照并发起审批
ApprovalResultEvent       平台回调或事件载荷
ApprovalStatus            通用审批状态
```

后续在本仓库实现审批引擎时，它可以实现 `ApprovalPlatformApi`，并通过 `ApprovalResultHandler` 注册表分发审批结束事件。正式拆分后，ERP 侧替换为审批中台 HTTP/消息客户端，业务模块无需修改其领域逻辑。

## 拆分步骤

1. 在审批中台仓库迁移流程定义、节点、审批人规则、实例、任务和操作记录表。
2. 将审批中台 API 按 `ApprovalPlatformApi` 暴露为 OpenAPI，保留字段语义和幂等键。
3. 将 `ApprovalResultEvent` 发布为可靠事件或 Webhook；中台持久化投递记录并支持重试。
4. 将组织人员、角色、部门和层级主管解析改为 `IdentityProvider` SPI 或远程 API，禁止查询 ERP 组织表。
5. ERP 增加审批平台客户端，实现超时、重试、签名认证和本地提交幂等。
6. ERP 将 `ApprovalResultHandler` 改为事件消费者，按 `eventId` 建立消费幂等记录。
7. 为每个接入业务注册数据快照、摘要和字段条件元数据；中台只保存和匹配通用字段值。
8. 灰度切换一个业务对象，核对实例状态、待办、回调重试和业务资格校验后再迁移其他项目。

## 事务与可靠性

审批中台事务与业务系统事务独立，不能使用跨库事务。推荐以下保证：

```text
业务系统提交审批
  → 保存本地提交幂等记录
  → 调用中台，携带 requestId
  → 保存 instanceId 和审批状态

审批中台审批通过
  → 持久化 ApprovalResultEvent
  → 至少一次投递
  → 业务系统按 eventId 幂等创建或原地更新
  → 成功确认；失败重试或人工补偿
```

业务系统不得在回调失败时将审批中台实例改回审批中；应通过重试、死信和人工补偿保证最终一致性。

## 身份与多租户

- 中台统一使用 `tenantId`，ERP 内部可映射自现有 `corpid`；
- 用户、角色、部门与主管关系由身份提供方按租户解析；
- 业务系统传入的是稳定用户标识，不能传展示名称作为审批依据；
- 审批任务生成时冻结实际审批人，之后的组织变动不修改历史审批任务；
- 接入认证应绑定调用方、租户和业务对象编码，防止跨租户提交或伪造结果回调。

## 验收清单

- 业务项目不依赖审批中台的数据库表或实体；
- 中台不依赖任一业务项目的单据、组织或权限实现；
- `requestId` 重复提交只产生一个审批实例；
- `eventId` 重复投递只产生一次业务生效；
- 已通过实例的流程版本、快照和审批人保持可追溯；
- 无审批人自动通过、会签、或签、撤回和拒绝均有不可变审计记录；
- 业务项目仅在 `NO_APPROVAL` 或 `APPROVED` 状态放行后续业务。

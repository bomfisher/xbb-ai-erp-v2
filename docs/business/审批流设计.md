# 审批流设计

## 适用范围

本文定义租户级业务单据审批能力的领域边界、流程配置、运行时实例、状态转换、页面入口和业务模块接入契约。审批决定数据是否可以成为有效单据版本；单据只有处于可用审批状态时，才允许参与后续业务流转。

本文中的“审批”不等同于业务单据的“确认”。审批是新建或编辑数据的生效前置流程；确认是正式单据进入履约、库存、结算或过账等业务环节前的业务复核动作。两者应分别建模。

审批中台的稳定业务接入契约见 `docs/guide/common/approval-platform/README.md`；独立服务拆分步骤见 `docs/guide/common/approval-platform/拆分指导.md`。

首期按“ERP 页面网关”运行：ERP 保留菜单和 `/erp/v1/approval/flow/*` 设置页接口，流程定义保存于 ERP 数据库。审批中台独立后，ERP 菜单和接口路径保持不变，由审批模块内部将请求转发给中台；ERP 不直接访问中台数据库。

## 已确认规则

1. 新建和编辑可以分别配置是否需要审批。
2. 审批流程支持成员、部门、角色范围，以及基于字段白名单的数据条件。
3. 一个流程可以配置多个顺序节点；节点支持会签和或签。
4. 审批人支持指定人员、指定角色、1 级主管、2 级主管等层级主管占位规则。
5. 提交人在审批结束前可以撤回。
6. 撤回实例可以复制为新草稿，再次提交时创建全新审批实例。
7. 最后一个节点完成后，审批实例变为已通过，并由业务模块原子地应用数据。
8. 审批状态为：无需审批、待审批、审批中、已通过、已拒绝、已撤回。
9. 只有无需审批和已通过的数据可以参与后续业务。
10. 同一单据同一审批场景不允许并行活动实例；审批中数据不可编辑、删除或参与业务。
11. 一个单据可以配置多个流程；已生效流程必须通过新版本修改，历史实例不受影响。
12. 设置页面维护流程，审批中心提供“我提交的”和“待我审批”入口。
13. 节点解析不到符合人员时自动通过，并写入原因和告警记录。
14. 已发生库存、结算、过账等下游业务的单据，首期禁止发起编辑审批。

## 业务流程

### 新建审批

```text
新建草稿 → 提交审批 → 匹配流程
  ├─ 无匹配流程：无需审批 → 创建正式单据
  └─ 命中流程：待审批/审批中 → 全部节点通过 → 创建正式单据并标记已通过
```

新建审批通过前不创建可参与业务的正式单据；审批实例保存完整数据快照。通过回调由业务模块创建正式单据，审批域不直接写采购、销售或库存表。

### 编辑审批

```text
已通过单据 V1 → 提交编辑审批（保存变更快照 V2）
  ├─ 审批中：原单据继续保留 V1，但不可编辑和参与业务
  ├─ 通过：原单据 ID 不变，事务内应用 V2
  └─ 拒绝/撤回：丢弃 V2，恢复为 V1 的已通过状态
```

“原地修改”表示审批通过后更新原单据，不表示提交审批时直接覆盖当前字段。审批期间必须隔离待审批快照，防止下游读取未生效数据。

## 审批状态

| 状态 | 说明 | 是否允许参与业务 |
| --- | --- | --- |
| `NO_APPROVAL` 无需审批 | 没有命中启用流程 | 是 |
| `PENDING_APPROVAL` 待审批 | 已提交，正在初始化首节点 | 否 |
| `IN_APPROVAL` 审批中 | 至少有一个待处理节点或任务 | 否 |
| `APPROVED` 已通过 | 最终节点完成 | 是 |
| `REJECTED` 已拒绝 | 节点拒绝，审批结束 | 否 |
| `WITHDRAWN` 已撤回 | 提交人主动撤回，审批结束 | 否 |

业务模块统一通过审批域契约判断：`NO_APPROVAL` 或 `APPROVED` 才具备业务资格。审批状态不替代订单履约、库存、结算、过账等业务状态。

## 流程配置

### 流程头

流程定义至少包含：

- `businessCode`：稳定单据业务编码；
- `approvalScene`：`CREATE` 或 `UPDATE`；
- `flowCode`、`flowName`：流程稳定标识和名称；
- `version`：从 1 递增的版本号；
- `priority`：多流程命中时的优先级；
- `scope`：发起人范围与数据条件；
- `status`：草稿、已生效、已停用、已归档。

同一租户、单据编码、场景、流程编码和版本唯一。已生效版本不可原地修改；修改时复制为下一版本草稿，发布新版本后旧版本停止接收新提交，但继续完成已有实例。

未启用草稿或已停用流程仅在不存在待审批或审批中实例时允许逻辑删除。逻辑删除后流程定义、节点和审批人不再用于列表和流程匹配；审批实例的流程详情必须读取实例创建时冻结的流程版本与节点快照，不能依赖仍存在的流程定义，因此历史审批单据仍可查看完整流程。

### 发起人范围

支持：

- 指定成员；
- 指定部门，可配置是否包含子部门；
- 指定角色；
- 条件分支至少包含两个出口：`如果` 与兜底的 `否则`；可按顺序追加多个 `否则如果` 分支。
- 每个非兜底分支可配置多条结构化条件，分支内条件同时满足后进入该分支。

### 数据范围

数据条件只能引用单据模块注册的审批字段白名单，例如金额、部门、仓库、币种。流程新建前先选择业务对象和审批场景，设置页再通过审批业务目录加载该业务的新建/编辑字段；条件分支和全局适用数据范围都保存为 `字段路径 + 操作符 + 值` 的结构化规则，不保存自由文本表达式。条件分支首期不开放 `BUSINESS`、`SERIAL_NO` 字段；日期字段使用日期选择器，避免依赖手工输入格式。服务端维护字段类型、操作符和取值规则；前端不得传数据库列名、SQL、任意 JSONPath 或过滤操作符。

流程匹配步骤为：租户 + 单据编码 + 场景 → 发起人范围 → 数据条件 → 按优先级选唯一流程。无匹配时为无需审批；同优先级命中多条属于配置冲突，拒绝提交并提示管理员。

## 节点与审批人

节点按 `nodeNo` 顺序执行，单节点配置：

- `ALL_SIGN` 会签：全部有效审批人同意才通过，任一人拒绝立即拒绝；
- `ANY_SIGN` 或签：任一人同意即通过，全部审批人拒绝才拒绝；
- 审批人规则：指定人员、指定角色、1 级主管、2 级主管等。

主管规则只保存层级占位，例如 `SUPERIOR(level=1)`；提交审批时按提交人的组织关系解析实际人员，并将候选人快照到运行时节点和任务。组织变更不影响历史审批。

节点解析出 0 个审批人时自动通过，必须记录流程版本、节点、解析规则、解析时间和“无符合人员”的原因，并向流程管理员产生告警。

## 运行时模型

建议审批能力独立归属 `xbb-erp-module-approval`，核心聚合和持久化对象如下：

| 对象 | 责任 |
| --- | --- |
| `ApprovalFlowDefinition` | 流程版本、范围、节点定义 |
| `ApprovalInstance` | 一次新建或编辑提交，冻结流程版本和数据快照 |
| `ApprovalInstanceNode` | 运行时节点、候选审批人和节点状态 |
| `ApprovalTask` | 分配给具体人员的待办 |
| `ApprovalActionRecord` | 提交、同意、拒绝、撤回、自动通过等不可变记录 |

审批实例至少保存：`corpid`、`businessCode`、`approvalScene`、`businessId`、`businessSnapshotJson`、`flowDefinitionId`、`flowVersion`、`submitterId`、`approvalStatus`、`currentNodeNo`、`sourceInstanceId`、提交/完成时间。

运行时任务必须保存解析后的 `assigneeId`，不能在审批时重新依据当前角色或主管关系计算。

## 撤回与复制

提交人只能在待审批或审批中撤回。撤回时取消未处理任务，实例变为已撤回并写入操作记录；不得复用原实例或原任务。

“基于撤回审批新建”通过复制快照实现：

```text
已撤回实例 A → 复制为可编辑草稿 B → 再次提交 → 新实例 C
```

实例 C 重新匹配当前生效的流程版本，并通过 `sourceInstanceId` 保留追溯关系。

## 审批中心

审批待办入口至少包含：

- **我提交的**：按提交人查询实例，展示单据摘要、状态、节点、版本、提交时间和撤回动作；
- **待我审批**：按当前人员任务查询待办，展示提交人、单据摘要、节点、会签/或签进度和处理动作。

详情页展示冻结快照、编辑差异、流程版本、节点进度、审批记录和自动通过原因。

## 页面与接口建议

### 审批设置

```text
POST /erp/v1/approval/flow/list
POST /erp/v1/approval/flow/detail
POST /erp/v1/approval/flow/save-draft
POST /erp/v1/approval/flow/publish
POST /erp/v1/approval/flow/create-next-version
POST /erp/v1/approval/flow/disable
POST /erp/v1/approval/flow/delete
```

页面按“单据 → 新建审批 / 编辑审批”组织，展示流程名称、优先级、范围、版本和状态；已生效版本只读。

### 审批中心

```text
POST /erp/v1/approval/todo/submitted-list
POST /erp/v1/approval/todo/pending-list
POST /erp/v1/approval/instance/detail
POST /erp/v1/approval/instance/withdraw
POST /erp/v1/approval/instance/copy-as-draft
POST /erp/v1/approval/task/approve
POST /erp/v1/approval/task/reject
```

### 业务模块接入

业务模块通过应用层端口接入审批域：

```text
submitApproval
canParticipateInBusiness
applyApprovedCreate
applyApprovedUpdate
```

`applyApprovedCreate` 和 `applyApprovedUpdate` 必须在审批实例完成与业务数据写入的事务边界内执行，并通过幂等键防止重复回调。

## 列表与操作权限

业务列表分为正常数据和审批中数据：

- 正常数据：正式单据审批状态为无需审批或已通过，可执行编辑、确认、下游引用、过账等操作；
- 审批中数据：来源为审批实例或带活动审批实例的单据，只读，可查看流程；仅提交人可撤回；
- 已拒绝、已撤回：作为审批历史展示，可复制为新草稿。

服务端必须校验活动审批实例和审批状态，不能依赖前端隐藏按钮实现并发与权限控制。

## 关键不变量

1. 同一租户、单据、场景最多一个活动审批实例。
2. 审批期间原单据当前有效版本不被编辑审批快照覆盖。
3. 最终节点只允许完成一次；完成后才触发业务回调。
4. 审批版本、快照、候选审批人和处理记录不可被后续配置或组织变更改写。
5. 审批域不直接访问业务模块 Mapper；业务模块不直接更新审批实例状态。
6. 所有业务入口都校验审批资格：仅无需审批或已通过可参与业务。
7. 无审批人自动通过必须有审计记录和告警。
8. 流程删除仅允许未启用或已停用且无活动实例的定义；相同流程编码重新创建时版本号必须基于包含逻辑删除记录的历史最大版本号递增；历史实例始终以冻结快照展示流程。

## 首期不支持

- 已产生下游业务影响单据的编辑审批；
- 同一单据并行多个新建或编辑审批实例；
- 审批通过后的反向自动冲销；
- 管理员在已生效版本上直接修改；
- 未经规则允许的自审、代审和跨租户审批。

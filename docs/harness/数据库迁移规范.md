# 数据库迁移规范

## 当前策略

当前采用方案 A：以授权的只读结构导出生成 `V1__baseline.sql`。Flyway 运行时启用仍属于待确认变更；启用前必须由数据库负责人确认应用入口和回滚策略，防止历史库被错误迁移。

## 新增迁移

- 管理端数据库迁移放在 `xbb-erp-app-admin/src/main/resources/db/migration/`，文件名使用 `V<递增版本>__<英文描述>.sql`。
- 初次基线只能执行一次 `scripts/export-flyway-baseline.sh --confirm-baseline`；脚本拒绝覆盖已有 `V1__baseline.sql`，并移除 `DROP TABLE`、会话指令和历史 `AUTO_INCREMENT` 值。
- 当前已生成的基线范围与来源见 `Flyway基线记录.md`；后续结构变更必须从 `V2__...sql` 开始。
- 一个迁移文件只完成一个可回滚的业务结构变化；同时维护受影响模块的 Repository、PO、Mapper XML、领域模型和测试。
- 迁移只写 DDL/DML，不写业务应用逻辑；禁止修改已在环境执行过的历史迁移文件。
- 新增或变更表时，保留 `docs/sql` 的可读设计说明，但以 Flyway 迁移文件作为实际执行事实源。

## 启用与发布

1. 在预发的数据库副本上执行 `flyway info` 与 `migrate`，确认 `flyway_schema_history` 和目标版本。
2. 首次接入历史库时，明确使用一次性基线迁移或受控 `baseline-on-migrate`，不得由 Agent 自行选择。
3. 生产发布前备份数据、验证 SQL 可在目标 MySQL 版本运行，并在交付报告记录迁移编号。

# 系统配置管理设计

## 适用范围

本文定义租户级系统配置管理能力的领域边界、页面交互、接口契约和数据结构。实际执行数据库结构以 Flyway 迁移为准；本文所列 SQL 是待评审的迁移内容，尚未写入迁移目录。

后端实现归属 `xbb-erp-module-system`，前端实现归属 `/Users/bomfish/xbb-ai-erp-v2-front`。各销售、采购、资金、库存和主数据模块只通过应用层配置查询 Port 消费已生效的配置值，不维护系统配置页面或配置持久化。

## 功能

- 主题：租户级系统配置管理。
- 目标用户与业务价值：管理员可以按业务大类和单据维护影响业务行为的系统参数，页面以统一的控件、提示和保存协议呈现，避免将参数散落在各业务单据页面。
- 涉及模块：`xbb-erp-module-system`、`xbb-erp-app-admin`、前端管理端；实际消费配置的业务模块按配置目录逐步接入。

## 领域边界

### 聚合根

`BusinessConfig` 是以 `(corpid, businessCode)` 唯一定位的租户配置聚合：

```text
租户 + 单据业务编码 -> 一个配置值 JSON 对象
```

- `corpid`：租户隔离键。
- `businessCode`：单据或业务对象的稳定编码，例如 `SALES_ORDER`、`SALES_OUTBOUND`、`SALES_INVOICE`。
- `configJson`：配置项编码到配置值的 JSON 对象，例如 `{"allowNegativeStock":false,"pricingMode":"ORDER_PRICE"}`。

配置的标题、帮助文本、控件类型、选项、默认值、可见性和校验规则不存数据库，而是在 `xbb-erp-module-system` 的配置目录中以代码定义。数据库只存租户覆盖值。这使新增字段不需要 DDL，且可避免租户自行篡改配置结构或帮助文案。

### 不包含的能力

- 本期不支持管理员自定义配置项、控件类型、选项或大类。
- 本期不支持配置历史版本、审批流、定时生效和跨租户复制。
- 不以系统配置替代单据字段、权限或审批流；单据业务规则仍由各自领域模块负责。

### 配置目录与值的关系

```text
代码配置目录
  大类（销售业务）
    单据（销售订单）
      分组（库存与履约）
        配置项定义（编码、标题、控件、帮助、默认值、校验）
                         +
数据库租户配置值
  corpid + SALES_ORDER -> { 配置项编码: 配置值 }
                         =
页面返回配置项定义 + 当前有效值
```

未保存过的配置项使用目录中声明的默认值。保存时只持久化与默认值不同的值；若全部恢复默认值，物理删除该租户的配置记录。删除是恢复默认值，不影响配置目录或其他租户。

## 页面与交互

### 左侧目录

左侧仅展示顶级业务目录，按以下稳定顺序排列：

1. 销售业务
2. 采购业务
3. 资金往来
4. 库存业务
5. 基础资料

选择大类后，右侧展示该大类下各单据的配置分组。单据显示顺序和可见性由服务端配置目录决定；前端不得硬编码单据枚举。

### 右侧内容

右侧按“单据卡片 -> 页面内分组 -> 配置项”的层级渲染。例如“销售业务”可以包含“销售订单”“销售出库”“销售发票”三张单据卡片；每张卡片中再按“价格与折扣”“库存与履约”“审核与单据控制”等分组分隔。

每个分组、配置项标题和选项均可以提供帮助文案。前端仅当对应 `helpText` 非空时显示小问号图标；悬浮或点击后显示该文案，避免无意义图标。

支持的控件协议：

| 控件类型 | 值类型 | 使用场景 |
| --- | --- | --- |
| `TEXT` | 字符串 | 文本、提示语、允许的业务前缀等 |
| `NUMBER` | 数字 | 天数、阈值、比例等 |
| `SWITCH` | 布尔 | 单一启用/停用开关 |
| `SELECT` | 字符串 | 单选下拉 |
| `MULTI_SELECT` | 字符串数组 | 多选下拉 |
| `CHECKBOX_GROUP` | 字符串数组 | 多个复选框 |
| `RADIO` | 字符串 | 单选按钮组 |

`TEXT`、`NUMBER`、`SWITCH`、`SELECT`、`MULTI_SELECT`、`CHECKBOX_GROUP` 与 `RADIO` 的配置项都可以带标题、项级帮助和选项级帮助；选项型控件必须返回非空选项列表。

### 保存交互

- 进入大类时请求该大类的目录和当前有效值；未覆盖的项直接展示默认值。
- 支持按单据卡片保存，提交时必须包含该单据的完整配置对象，避免页面局部更新覆盖同一单据的其他项。
- 保存成功后以服务端返回的有效值刷新页面。
- 服务端拒绝未知 `businessCode`、未知配置项、错误值类型、未声明的选项值和当前租户无权维护的目录。

## 接口契约

接口均归属 `/erp/v1/system/businessConfig`，请求 DTO 继承 `BaseDTO` 并通过 `corpid` 实现租户隔离。

| 接口 | 用途 | 核心请求 | 核心响应 |
| --- | --- | --- | --- |
| `POST /catalog` | 加载左侧目录 | `corpid` | 大类 `code`、`name`、`helpText` |
| `POST /detail` | 加载一个大类右侧的全部单据、分组、定义与有效值 | `corpid`、`categoryCode` | 单据、分组、配置项元数据、`value` |
| `POST /save` | 保存一个单据的配置覆盖值 | `corpid`、`businessCode`、`values` | 保存后的单据有效配置 |

接口原子文档：`docs/api/endpoints/system-business-config-catalog.md`、`docs/api/endpoints/system-business-config-detail.md`、`docs/api/endpoints/system-business-config-save.md`。

`/detail` 的配置项结构建议如下：

```json
{
  "code": "stockDeductionTiming",
  "title": "库存扣减时点",
  "helpText": "确定销售出库单在哪个业务节点扣减可用库存。",
  "controlType": "RADIO",
  "required": true,
  "value": "AUDIT",
  "defaultValue": "AUDIT",
  "options": [
    {
      "value": "AUDIT",
      "label": "审核时扣减",
      "helpText": "审核成功后立即扣减。"
    },
    {
      "value": "POST",
      "label": "过账时扣减",
      "helpText": "过账成功后再扣减。"
    }
  ]
}
```

上例仅说明协议形态，不代表已确认的库存扣减业务规则。每个实际配置项的编码、默认值、选项和被消费的业务语义，必须在开发前由对应业务负责人确认。当前已确认并落地销售发票配置 `SALES_INVOICE_AUTO_CREATE_RECEIVABLE`：过账后自动生成应收，布尔开关，默认关闭；开启后由销售发票过账流程调用结算模块的应收创建契约。

## 数据设计

### 建表 SQL（待评审）

当前目录的最高版本为 `V23`，落地时建议新建 `xbb-erp-app-admin/src/main/resources/db/migration/V24__create_business_config_table.sql`，内容如下：

```sql
CREATE TABLE sys_business_config (
    id BIGINT NOT NULL AUTO_INCREMENT,
    corpid VARCHAR(64) NOT NULL COMMENT '租户标识',
    business_code VARCHAR(64) NOT NULL COMMENT '业务单据编码',
    config_json JSON NOT NULL COMMENT '非默认配置值对象，键为配置项编码',
    del TINYINT NOT NULL DEFAULT 0 COMMENT '删除标记：0否，1是',
    add_time BIGINT NOT NULL COMMENT '创建时间戳（毫秒）',
    update_time BIGINT NOT NULL COMMENT '更新时间戳（毫秒）',
    PRIMARY KEY (id),
    UNIQUE KEY uk_sys_business_config_corpid_code (corpid, business_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='租户业务系统配置';
```

选择 MySQL `JSON` 而非 `TEXT` 的原因：数据库可保证保存内容是合法 JSON；查询时仍由应用层以 `corpid + business_code` 精确定位，不允许依据 JSON 内容构造动态 SQL。现阶段不建立 JSON 路径索引，后续仅当产生明确的配置统计查询需求时再评估生成列和索引。

软删除行不应与同一租户和业务编码的新行并存，保存实现应复用已删除记录或恢复其 `del=0`，保持唯一索引的有效性。

> 发布前置条件：当前迁移目录同时存在 `V22__create_receipt_writeoff_table.sql` 和 `V22__extend_biz_no_rule_settings.sql` 两个版本号重复的文件。Flyway 会拒绝该状态；必须由数据库负责人确认其中一个尚未执行的迁移应使用的正确版本号，再新增本表迁移。本文不擅自修改既有迁移历史。

## 公共枚举、类型化结果与策略

### 配置键枚举

公共配置键只在 `xbb-erp-module-system-contract` 维护。每个枚举值既是前端/数据库的稳定配置编码，也是业务代码取得强类型结果的唯一入口；禁止业务模块以字符串拼接配置编码或将 JSON 自行反序列化。

建议定义泛型配置键接口和枚举：

```java
public interface BusinessConfigKey<T> {
    String code();
    BusinessCodeEnum businessCode();
    Class<T> valueType();
    T defaultValue();
}

public enum ApprovalConfigKeyEnum implements BusinessConfigKey<ApprovalMode> {
    PURCHASE_INBOUND_APPROVAL_MODE(
        BusinessCodeEnum.PURCHASE_INBOUND, ApprovalMode.class, ApprovalMode.REQUIRED
    ),
    SALES_ORDER_APPROVAL_MODE(
        BusinessCodeEnum.SALES_ORDER, ApprovalMode.class, ApprovalMode.REQUIRED
    ),
    SALES_OUTBOUND_APPROVAL_MODE(
        BusinessCodeEnum.SALES_OUTBOUND, ApprovalMode.class, ApprovalMode.REQUIRED
    );
}
```

实际代码不应让调用方使用 `BusinessConfigKey<?>` 取得值，而是提供泛型方法：

```java
public interface BusinessConfigQueryApi {
    <T> T get(String corpid, BusinessConfigKey<T> configKey);
}

ApprovalMode approvalMode = businessConfigQueryApi.get(
    corpid, ApprovalConfigKeyEnum.PURCHASE_INBOUND_APPROVAL_MODE
);
```

Java 枚举不能让每个枚举项天然保留不同的泛型参数，因此按值类型维护独立枚举。例如布尔开关使用 `BooleanConfigKeyEnum implements BusinessConfigKey<Boolean>`，金额/天数使用 `IntegerConfigKeyEnum implements BusinessConfigKey<Integer>`，审核模式使用 `ApprovalConfigKeyEnum implements BusinessConfigKey<ApprovalMode>`。不得在业务代码中进行 `Object` 强制转换。

### 策略结果

配置原始值和业务策略结果必须分离。配置查询 API 的职责是按枚举返回原始强类型值；策略 API 的职责是根据原始值及当前业务上下文返回业务可直接使用的结果对象。因此同一系统支持不同返回类型，而不污染统一查询 API。

```text
业务模块
  -> BusinessConfigQueryApi.get(corpid, 配置键)       # 取得强类型原始值
  -> XxxConfigPolicy.resolve(corpid, 上下文)           # 取得业务策略结果
  -> 执行业务动作
```

建议首批策略类型如下：

| 策略 | 消费配置 | 返回类型 | 使用位置 |
| --- | --- | --- | --- |
| `PurchaseInboundApprovalPolicy` | `PURCHASE_INBOUND_APPROVAL_MODE` | `boolean` | 采购入库提交后是否进入审核 |
| `SalesOrderApprovalPolicy` | `SALES_ORDER_APPROVAL_MODE` | `boolean` | 销售订单提交后是否进入审核 |
| `SalesOutboundApprovalPolicy` | `SALES_OUTBOUND_APPROVAL_MODE` | `boolean` | 销售出库提交后是否进入审核 |
| `InventoryNegativeStockPolicy` | 待确认的库存负库存配置 | `NegativeStockDecision` | 校验是否允许、是否需要提示、拒绝原因 |
| `DocumentPricePolicy` | 待确认的价格来源/变更配置 | `PriceDecision` | 返回允许修改、价格来源与重算要求 |

`NegativeStockDecision`、`PriceDecision` 是明确命名的不可变结果对象，不能以多个无语义的布尔参数替代。例如负库存策略可同时返回 `allowed`、`warningRequired` 和 `message`；价格策略可返回 `editable`、`source` 和 `recalculateRequired`。这些策略均由其所属业务模块实现，系统模块只提供配置查询契约，避免系统模块依赖销售、采购或库存领域。

### 目录定义的分层

系统模块的 `BusinessConfigCatalog` 是配置元数据唯一事实源。每个配置键在目录中声明所属大类、单据、分组、标题、帮助、控件和选项；公共枚举只维护稳定编码、所属单据、类型和默认值。目录启动时必须校验两者一一对应，避免出现可保存但业务无法读取或业务可读取但页面未注册的配置。

```text
xbb-erp-module-system-contract
  BusinessConfigKey<T>、各值类型配置键枚举、结果类型、BusinessConfigQueryApi

xbb-erp-module-system
  BusinessConfigCatalog、JSON 类型编解码、持久化、缓存失效、管理端接口

xbb-erp-module-sales / purchase / inventory
  业务策略实现；仅依赖 system-contract 并调用 BusinessConfigQueryApi
```

## 首期配置建议

以下是基于当前已有业务代码得到的候选配置清单，不代表已生效的业务规则。标为“可首批接入”的项已有明确策略接入点；标为“待业务确认”的项必须先确认语义、默认值和单据状态影响范围后再登记枚举。

| 大类 | 单据 | 配置项 | 控件 | 推荐默认值 | 状态 |
| --- | --- | --- | --- | --- | --- |
| 全局配置 | 采购订单、采购入库单、采购发票 | 自动审核 | 复选框：勾选表示自动审核 | 未勾选 | 统一保存 |
| 全局配置 | 销售订单、销售出库单、销售发票 | 自动审核 | 复选框：勾选表示自动审核 | 未勾选 | 统一保存 |
| 全局配置 | 预付款、应付款、付款单、付款核销 | 自动审核 | 复选框：勾选表示自动审核 | 未勾选 | 统一保存 |
| 全局配置 | 预收款、应收款、收款单、收款核销 | 自动审核 | 复选框：勾选表示自动审核 | 未勾选 | 统一保存 |
| 销售业务 | 销售发票 | 过账后自动生成应收 | 开关 | 关闭 | 已接入过账流程 |
| 销售业务 | 销售订单 | 允许超可用库存下单 | 开关 | 不允许 | 待确认，涉及预占策略 |
| 销售业务 | 销售出库 | 允许负库存出库 | 开关/单选策略 | 不允许 | 待确认，涉及库存账务 |
| 销售业务 | 销售订单 | 订单行价格来源 | 单选：客户价格/手工录入/取最低价等 | 待确认 | 待价格体系确认 |
| 销售业务 | 销售发票 | 开票来源范围 | 多选：订单/出库/手工等 | 待确认 | 待开票业务规则确认 |
| 资金往来 | 收款单 | 是否允许预收款 | 开关 | 允许 | 待资金业务确认 |
| 基础资料 | 客户/供应商/产品 | 编码生成方式 | 单选或文本组合 | 系统生成 | 与现有编号规则边界待确认 |

编号前缀、日期位、流水位数和流水规则继续由现有 `sys_biz_no_rule` / `BizNoService` 管理，不重复登记到本系统配置表；两者在菜单可以同属于系统管理，但其领域模型与保存接口独立。

当前 `DefaultPurchaseInboundApprovalPolicy` 的注释写明“未接入审批配置前默认要求审核”，实际返回值却为 `false`。在将采购入库审核方式接入系统配置前，必须由业务负责人确认 `false` 的准确语义及当前提交后的动作，不能根据注释或建议默认值直接改变线上行为。

## 缓存设计

配置结果使用 Redis 作为跨节点共享缓存，数据库是唯一持久化事实源。缓存存储的是“目录默认值与租户覆盖值合并后的强类型配置快照”，不是原始请求，也不缓存 Controller 的 VO。

| 项目 | 设计 |
| --- | --- |
| 缓存键 | `erp:system:business-config:{corpid}:{businessCode}` |
| 缓存值 | 该单据全部已校验的配置编码和值的 JSON 快照 |
| 读取 | 先读 Redis；未命中时查询单条配置记录、按目录合并默认值、校验并回填缓存 |
| 写入 | 数据库事务提交成功后删除该 `corpid + businessCode` 缓存；下次读取重建 |
| TTL | 24 小时，作为异常失效保护；不得仅依赖 TTL 保证配置变更生效 |
| 并发 | 相同配置首次加载使用短时互斥锁或 Spring 缓存同步机制，避免缓存击穿 |
| 故障 | Redis 不可用时回源数据库；配置管理保存仍以数据库事务为准，记录告警并允许后续读取重建缓存 |

缓存失效必须在事务提交后执行；事务回滚不得删除有效缓存。若以后引入异步消息或多级本地缓存，消息载荷至少包括 `corpid`、`businessCode` 和配置版本，消费者只做同键失效，不能以全量清空替代精确失效。

## 校验与安全

- `businessCode`、配置项编码、控件类型和选项值均由后端目录白名单控制。
- 保存前根据目录声明校验 JSON 值的类型、必填性、数值范围、文本长度及选项集合；不信任前端下发的标题、帮助、默认值或选项。
- 所有查询和保存都校验 `corpid`；业务配置仅允许租户内读取和修改。
- 配置被业务模块消费时，业务模块必须使用默认值兜底，避免历史租户未保存配置时出现空值行为。
- 配置语义改变、选项移除或默认值调整需做兼容评估；不得静默将已保存的旧值映射成未知行为。
- 管理端菜单由 `/erp/v1/menu/list` 动态下发，需由权限管理员增加“系统管理 / 系统配置”菜单权限，`routePath` 固定为 `/management/system/business-config`；前端路由已注册该地址，未授权菜单不会出现在侧栏。

## 待确认项

实现前需要逐项确认以下业务事实，不能由页面结构推断：

1. 五个业务大类下首期纳入哪些单据；当前已明确的销售单据为销售订单、销售出库、销售发票。
2. 每张单据的配置项编码、标题、帮助、默认值、控件类型、选项与校验规则。
3. 每个配置项由哪个业务动作消费，以及配置变更对草稿、已审核和已过账单据的生效边界。
4. 系统配置的菜单权限和保存权限编码。
5. 是否需要在首期记录操作审计；若需要，应复用项目既有审计机制，不能仅依赖 `update_time`。

## 验收标准

- 管理员可在左侧切换五类业务目录，右侧只显示所选目录下已注册单据的配置卡片与分组。
- 每个配置项都有标题；存在帮助文案的分组、配置项和选项均展示可访问的小问号说明。
- 所有七种控件可以根据服务端元数据渲染，并正确回显与提交对应的标量或数组值。
- 未保存过的租户展示默认值；保存后刷新仍展示该租户覆盖值；恢复默认值后删除覆盖数据并重新展示默认值。
- 非法业务编码、配置项、选项值、值类型和跨租户请求均被拒绝。
- 系统模块的单元测试覆盖目录合并、默认值、保存校验与恢复默认值；接口契约变更补充 API 原子文档、聚合文档和导航。

# 客户列表行内编辑与通用操作列设计文档

## 2. 背景与目标

当前客户列表页已经完成列表查询、动态筛选、顶部按钮与新建抽屉能力，但仍存在以下缺口：

- 列表缺少单行上下文动作入口，无法从列表直接发起编辑
- 当前 `ADD` 已接入右侧新建抽屉，但编辑态尚未接通
- 表格底层没有统一“行内操作列”能力，其他单据后续仍会重复建设
- 列表元数据当前只覆盖表头、顶部按钮、底部按钮，缺少单行动作元数据协议

本次目标如下：

1. 在客户列表页接通行内 `编辑` 入口
2. 复用现有右侧新建抽屉，演进为 `create / edit` 双模式抽屉
3. 在前端列表底层沉淀可复用的“通用操作列”能力
4. 在后端列表元数据体系中补齐“rowAction” 单行动作协议
5. 让客户成为首个接入方，但底层方案可直接复用到其他单据列表页

## 3. 设计范围

### 3.1 本次范围

本次仅包含以下内容：

- 客户列表增加最后一列 `操作` 列
- 操作列固定在表格右侧
- 行内动作采用“主动作直出 + 更多菜单”的统一形态
- 客户首版接通 `编辑` 动作
- 客户编辑复用现有抽屉组件并改造成双模式
- 新增或扩展后端行内动作元数据协议
- 前端表格底层抽取通用行内操作组件

### 3.2 非目标

本次不包含以下内容：

- 客户删除、停用、提交审核等其他动作正式落地
- 行点击即编辑
- 前端本地硬编码权限判断
- 详情抽屉模式
- 批量行操作
- 非客户页面的同步接入实现

## 4. 设计结论

### 4.1 操作列位置结论

客户列表行内编辑入口放在表格最后一列，列名统一为 `操作`。

采用该位置的原因如下：

- 行内编辑属于当前行上下文动作，天然适合放在单行尾部
- 与顶部按钮区形成明确分工：顶部放全局动作，行尾放单行动作
- 这是最容易沉淀为平台统一规范的位置，其他单据可直接复用

### 4.2 操作列冻结结论

操作列采用右侧固定策略：

- 当表格发生横向滚动时，`操作` 列固定在最右侧
- 当表格列较少、未产生横向滚动时，仍按同一列结构渲染，只是不强调冻结感知
- 操作列使用固定宽度，避免不同页面文案差异导致表格抖动

该策略的核心目的是保证用户在宽表场景下仍能稳定触达 `编辑` 等高频动作。

### 4.3 行内动作展示策略结论

本次采用“主动作直出 + 更多菜单”的统一策略。

统一规则如下：

- 每行默认直出 `1` 个高频主动作
- 其余动作收纳到 `更多` 菜单中
- 客户首版仅下发 `编辑`，因此首版表现为单个 `编辑` 按钮
- 后续如增加 `停用`、`删除`、`提交` 等动作，再按元数据决定哪些进入 `更多`

这样既满足客户当前高频编辑场景，也为后续多动作列表页预留统一扩展路径。

### 4.4 动作来源结论

行内动作项统一由后端元数据下发，不由前端页面本地硬编码。

核心结论如下：

- 前端底层负责渲染操作列与动作交互结构
- 后端负责定义当前列表有哪些动作、顺序如何、哪些动作直出、哪些动作进入 `更多`
- 前端不根据页面名称猜测动作集合，也不自行决定哪个动作更重要

该结论与现有 `header / topButton / bottomButton` 元数据体系保持一致，有利于列表元数据整体统一。

## 5. 后端元数据协议设计

### 5.1 协议定位

在现有列表元数据体系中新增一类元数据：`rowAction`。

其职责是描述某个业务列表“单行可执行动作定义”。

前端表格底层在发现 `rowAction` 非空时，自动补出最后一列 `操作` 列；动作项如何展示完全依赖 `rowAction` 元数据。

### 5.2 最小协议字段

`rowAction` 首版建议至少包含以下字段：

- `actionCode`：动作编码，例如 `EDIT`
- `actionName`：动作显示文案，例如 `编辑`
- `sort`：动作排序
- `showMode`：展示方式，首版建议支持 `PRIMARY`、`MORE`
- `bizStatusScope`：动作适用状态范围，便于后续按状态控制可见性
- `confirmType`：是否需要二次确认，便于后续承接删除、停用等风险动作

如果现有列表按钮元数据模型已足够接近，可优先扩展现有模型，而不是平行新造一套完全不同结构。

### 5.3 客户首版下发策略

客户列表首版只下发一个行内动作：

- `actionCode=EDIT`
- `actionName=编辑`
- `showMode=PRIMARY`

这样前端首版操作列会稳定直出 `编辑`。

后续如果客户列表增加其他动作，例如 `停用`、`删除`、`启用`，则由后端继续在 `rowAction` 中下发，并通过 `showMode` 指定其是直出还是进入 `更多`。

### 5.4 展示决策归属

“哪个动作直出、哪个动作进更多”必须由后端元数据明确表达，而不是由前端自行拍脑袋决定。

原因如下：

- 不同单据页的主动作不同
- 同一页面在不同业务状态下的主动作也可能不同
- 由后端统一表达更容易与权限、状态、业务配置保持一致

## 6. 前端通用底层设计

### 6.1 组件拆分结论

前端建议拆为三层：

1. `ListDataTable`：继续负责通用表格渲染，并新增右侧固定操作列能力
2. `ListRowActions`：新增通用行内操作组件，负责渲染“主动作 + 更多菜单”
3. 页面装配层：负责接收元数据、响应动作事件、串联业务抽屉

### 6.2 `ListDataTable` 职责边界

`ListDataTable` 新增职责：

- 接收行内动作元数据
- 在有动作元数据时自动渲染最后一列 `操作`
- 支持操作列固定在右侧
- 将某一行动作点击事件抛给上层页面

`ListDataTable` 不负责：

- 解释 `EDIT` 属于哪个业务模块
- 直接打开客户抽屉
- 直接调用业务接口

### 6.3 `ListRowActions` 职责边界

`ListRowActions` 专注负责：

- 解析直出主动作
- 渲染 `更多` 菜单
- 统一处理按钮与菜单项样式
- 点击后抛出统一事件

它不关心客户、供应商、采购等业务语义，只消费当前行和行动作元数据。

### 6.4 事件协议建议

建议统一抛出如下语义的事件：

```text
row-action => { actionCode, row }
```

其中：

- `actionCode`：后端下发的动作编码
- `row`：当前行完整数据

这样页面装配层只需要监听一个统一事件，再根据 `actionCode` 做业务编排。

## 7. 客户编辑抽屉设计

### 7.1 抽屉复用结论

客户编辑不新建第二套抽屉，而是复用现有新建抽屉，将其演进为 `create / edit` 双模式。

推荐原因如下：

- 新建与编辑共享同一套字段元数据结构
- 新建与编辑共享同一套动态表单分组逻辑
- 避免后续同一业务出现两套字段渲染与保存逻辑分叉
- 符合“复用现有新建侧开抽屉改成编辑抽屉”的已确认方向

### 7.2 抽屉模式定义

统一抽屉建议支持两种模式：

- `mode=create`：请求 `POST /erp/v1/customer/addItem`
- `mode=edit`：请求 `POST /erp/v1/customer/updateItem`

两种模式共享：

- 抽屉壳布局
- 字段分组渲染
- 通用动态表单能力
- 提交成功后的刷新通知机制

两种模式差异：

- 标题文案不同
- 初始化接口不同
- 编辑态额外需要传入当前行 `id`
- 编辑态初始化数据由 `updateItem` 回填

### 7.3 页面编排流程

客户列表页建议按以下流程接入：

1. 页面加载时获取列表数据与 `rowAction` 元数据
2. 将 `rowAction` 传给表格底层
3. 用户点击某一行 `编辑`
4. 表格底层抛出 `row-action`
5. 列表页识别 `actionCode=EDIT`
6. 打开客户抽屉，并传入 `mode=edit` 与当前行 `id`
7. 抽屉内部请求 `POST /erp/v1/customer/updateItem`
8. 编辑成功后抛出 `saved`
9. 列表页收到 `saved` 后刷新列表

## 8. 异常处理与边界约束

### 8.1 元数据异常处理

当 `rowAction` 元数据获取失败时：

- 不影响列表主数据展示
- 行内操作列可以降级为不展示
- 不允许前端自动猜测本应出现的动作集合

### 8.2 未知动作处理

如果后端下发了前端当前尚未接入的 `actionCode`：

- 前端底层忽略该动作，不执行猜测逻辑
- 开发态可以输出告警，便于联调排查
- 线上不让未知动作变成误触发风险

### 8.3 编辑初始化失败处理

点击 `编辑` 后，如果 `POST /erp/v1/customer/updateItem` 失败：

- 错误只在抽屉内部展示
- 列表页保持原状
- 关闭后重新打开时重新发起请求

### 8.4 交互边界

本次明确以下边界：

- 不做整行点击即编辑
- 不做前端本地权限兜底
- 不提前落地删除、停用、提交等其他动作
- 不在列表页写死客户专属操作列逻辑

## 9. 测试与验收

### 9.1 前端底层测试

至少覆盖以下场景：

- 有 `rowAction` 元数据时自动渲染 `操作` 列
- `操作` 列固定在右侧
- 仅有一个 `PRIMARY` 动作时直出按钮
- 存在多个动作时渲染“主动作 + 更多”
- 点击动作后正确抛出 `{ actionCode, row }`

### 9.2 客户页面测试

至少覆盖以下场景：

- 客户列表页能正确获取并传递 `rowAction`
- 点击某行 `编辑` 后能打开抽屉
- 抽屉以 `edit` 模式初始化
- 编辑成功后列表触发刷新

### 9.3 抽屉测试

至少覆盖以下场景：

- `create` 模式请求 `addItem`
- `edit` 模式请求 `updateItem`
- 编辑态可正确接收并使用当前行 `id`
- 初始化失败时显示错误态
- 成功保存后抛出 `saved`

### 9.4 联调验收标准

验收标准如下：

1. 客户列表最后一列出现右侧固定 `操作` 列
2. 客户列表每行可直接点击 `编辑`
3. 点击 `编辑` 后复用现有右侧抽屉进入编辑态
4. 编辑态初始化接口使用 `POST /erp/v1/customer/updateItem`
5. 行内动作集合完全由后端元数据驱动
6. 表格底层能力可直接复用到其他单据列表页

## 10. 实施建议

建议按以下顺序实施：

1. 后端补充 `rowAction` 元数据协议与客户首版下发
2. 前端扩展 `ListDataTable` 支持右侧固定操作列
3. 前端新增 `ListRowActions` 通用组件
4. 客户列表页接入 `rowAction` 并监听统一事件
5. 客户抽屉改造为 `create / edit` 双模式
6. 接通 `POST /erp/v1/customer/updateItem`
7. 补齐前端组件测试与客户页面测试

## 11. 最终结论

本次客户列表编辑入口采用“列表最后一列固定操作列 + 后端元数据驱动动作项 + 复用现有抽屉进入编辑态”的方案。

其中：

- 操作列统一放在表格最后一列，并固定在右侧
- 行内动作采用“主动作直出，其余进入更多”的平台统一形态
- 动作集合不由前端硬编码，而由后端 `rowAction` 元数据下发
- 前端沉淀 `ListDataTable + ListRowActions + 页面装配层` 三层复用结构
- 客户编辑复用现有新建抽屉，统一演进为 `create / edit` 双模式

该方案既能快速落地客户当前的行内编辑需求，也能为后续其他单据页复用统一操作列能力提供稳定底座。

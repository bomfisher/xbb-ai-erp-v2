# 接口主次文档生成 Skill 设计说明

## 1. 背景

当前仓库中的接口文档已经开始形成两类形态：

- 按业务组织的主文档，例如 `docs/api/customer-customer.md`
- 按功能或公共场景组织的次文档，例如 `docs/api/common-list.md`

这两类文档都对 AI 编程有价值，但如果没有统一边界，长期会出现几个问题：

- 同一接口在多个文档里重复维护
- 主文档和次文档信息逐步漂移
- 新增接口时不知道先更新哪一份文档
- AI 在读取文档时无法判断哪一份才是事实源
- 业务中文名、文件名、代码标识之间可能无法稳定对应

因此需要设计一个新的通用 skill，用于根据用户输入的主题、范围和要求，生成或更新“主文档 + 次文档”结构，并明确主次文档边界、输入规则、冲突处理规则与待确认机制。

## 2. 目标

本设计希望建立一个通用 skill，负责以下能力：

- 根据用户输入生成或更新业务主文档
- 根据用户输入生成或更新功能索引次文档
- 保证主文档是唯一事实源，次文档只承担索引职责
- 支持结构化输入与自然语言输入
- 支持新建、增量更新、重写前确认三种处理模式
- 支持候选值发现与待确认输出，但不把候选值伪装成已确认事实
- 仅依赖用户输入、当前仓库现有文档与当前仓库代码事实，不内置具体业务词映射知识

## 3. 非目标

第一版明确不做以下事情：

- 不内置“采购 = purchase”“客户 = customer”之类固定业务映射词典
- 不做跨仓库知识复用
- 不通过翻译、拼音或语义猜测自动生成业务标识
- 不自动修复所有旧文档结构问题
- 不把主文档完整内容复制到次文档
- 不在证据不足时直接生成看似完整的事实文档
- 不覆盖用户已有内容而不提示

第一版只解决“主次文档边界统一 + skill 生成流程统一”的问题。

## 4. 核心原则

### 4.1 主文档是唯一事实源

主文档按业务维度组织，负责沉淀接口完整事实，包括：

- 完整路径
- 请求方式
- 入参 DTO
- 用途
- 请求示例
- 响应示例
- 参数说明或字段说明
- 规则说明或限制说明
- 与其他接口的调用关系

同一个接口的完整正文，在整个仓库中只能存在一个归属点。

### 4.2 次文档是功能索引层

次文档按功能或公共场景组织，例如列表、详情、菜单等。

次文档只维护以下信息：

- 所属业务
- 接口完整路径
- 请求方式
- 一句话用途
- 与同类接口相比的差异点
- 指向主文档的定位信息

次文档不维护完整请求示例、完整响应示例或大段字段说明。

### 4.3 不凭猜测补事实

skill 只能从以下三类来源获得事实：

- 用户显式输入
- 当前仓库现有文档
- 当前仓库代码事实

如果某个结论只能靠语义猜测得到，则该结论只能作为候选值，不能直接写入正式文档。

### 4.4 候选值必须带来源

凡是不确定的信息，都必须显式记录：

- 候选值本身
- 候选值来源
- 为什么需要人工确认

例如：

- 待确认：主题标识候选为 `purchase`；来源：`docs/api/purchase-purchase-01.md` 文件名
- 待确认：主文档候选为 `purchase-purchase-01.md` 与 `purchase-purchase-02.md`；来源：现有文档目录

## 5. 输入模型

### 5.1 输入形式

skill 同时支持两种输入：

- 结构化输入
- 自然语言输入

结构化输入优先；自然语言输入先解析，再转为内部统一模型。

### 5.2 内部统一输入模型

skill 内部统一解析为以下字段：

- `subject`：主题标识，例如用户提供的英文 slug 或其他稳定标识
- `subjectLabel`：主题中文名，例如“采购”“客户”
- `scope`：文档范围，例如 `list`、`create`、`edit`、`detail`
- `docMode`：`main`、`secondary`、`both`
- `requirements`：额外要求，例如“补齐完整路径”“优先增量更新”“只生成骨架”

### 5.3 缺失字段处理

如果缺失关键字段，skill 不允许硬猜，必须反问用户。

关键字段包括：

- 至少一个主题识别字段：`subject` 或 `subjectLabel`
- 至少一个范围字段：`scope`
- 至少一个输出模式字段：`docMode`

## 6. 通用映射机制

### 6.1 不内置具体业务映射

skill 不维护任何具体业务映射词典。

例如：

- 不内置“采购 -> purchase”
- 不内置“客户 -> customer”
- 不内置“供应商 -> supplier”

### 6.2 允许候选发现，不允许自动拍板

当用户只输入中文名或只输入英文标识时，skill 可以去以下位置寻找候选：

- `docs/api/*.md`
- `docs/superpowers/specs/*.md`
- 相关 controller、DTO、VO、URL
- 相关业务枚举或模块名

如果多个来源一致，可以自动采用。

如果多个来源冲突，或者没有任何来源足够稳定，则必须反问用户。

### 6.3 映射的本质

skill 不负责“翻译业务名”，只负责：

- 发现候选
- 交叉验证
- 维持文档与代码的一致性

## 7. 主文档规范

### 7.1 组织方式

主文档按业务维度组织。

文档标题建议统一为：

- `<主题中文名>模块接口`

主文档内部按功能分章节，例如：

- 列表
- 新建
- 编辑
- 详情
- 删除
- 启停用
- 导入导出

### 7.2 接口标准块

每个接口在主文档中建议统一采用以下结构：

- 接口完整路径
- 请求方式
- 入参 DTO
- 用途
- 请求示例
- 响应示例
- 参数说明或字段说明
- 规则说明或限制说明

### 7.3 更新规则

- 如果主文档不存在，则新建
- 如果主文档存在且结构匹配，则增量更新
- 如果主文档存在但结构明显不匹配，则先提示用户确认是否重写

## 8. 次文档规范

### 8.1 组织方式

次文档按功能或公共场景组织，例如：

- `common-list.md`
- `common-detail.md`
- `common-menu.md`

### 8.2 记录结构

每条索引记录至少包含：

- 所属业务
- 接口完整路径
- 请求方式
- 一句话用途
- 差异点摘要
- 主文档定位

### 8.3 更新规则

- 次文档默认走增量更新
- 次文档不主动整体重写
- 如果主文档缺失，次文档只能标注“主文档待补”，不能自己扩写完整正文

## 9. 生成与更新流程

### 9.1 Step 1：解析输入

先把用户输入解析成统一模型：

- `subject`
- `subjectLabel`
- `scope`
- `docMode`
- `requirements`

### 9.2 Step 2：扫描现有事实源

按顺序扫描：

- 现有主文档
- 现有次文档
- 相关 spec / plan
- 相关 controller、DTO、VO、URL、业务枚举

### 9.3 Step 3：建立文档对象模型

判断本次范围需要落到：

- 哪个主文档
- 主文档的哪些章节
- 哪些次文档索引

### 9.4 Step 4：决定处理模式

根据扫描结果，判断本次处理模式是：

- 新建
- 增量更新
- 结构冲突，等待用户确认后重写

### 9.5 Step 5：先主后次

如果 `docMode=both`，则必须遵守以下顺序：

1. 先生成或更新主文档
2. 再根据主文档结果同步生成或更新次文档

### 9.6 Step 6：输出结果摘要

skill 结束时统一输出：

- 新建了哪些文档
- 更新了哪些文档
- 更新了哪些章节
- 哪些内容来自代码
- 哪些内容来自现有文档
- 哪些内容需要人工确认

## 10. 冲突处理规则

以下情况必须暂停并反问用户：

- 主文档候选不唯一
- 主题中文名与主题标识无法稳定对应
- 代码与文档冲突且无法判断哪边应优先
- 旧文档结构不匹配，可能需要整体重写
- `scope` 无法稳定识别

以下情况允许继续，但必须显式标注“待确认”：

- 只找到接口路径，未找到稳定的入参或出参结构
- 只找到部分章节归属证据
- 找到候选值，但证据不足以直接确认

## 11. 待确认格式

skill 对不确定项统一采用固定格式输出，例如：

- `待确认：主文档归属候选为 A / B；来源：docs/api/...、Controller ...`
- `待确认：接口完整路径候选为 ...；来源：已有文档标题或代码注解`
- `待确认：该接口是否应纳入 detail 次文档；原因：仅发现详情查询语义，未发现页面说明`

待确认内容不能被直接写成正式事实。

## 12. 输出模板

skill 完成后统一输出以下摘要：

- 新建文档列表
- 更新文档列表
- 更新章节列表
- 事实来源说明
- 待确认项列表

这样用户可以快速确认本次变更边界，而不需要重新阅读全文。

## 13. 推荐方案与结论

本设计最终采用“双维组织，单一事实源”方案：

- 主文档按业务组织
- 次文档按功能组织
- 同一接口完整正文只在主文档维护一次
- 次文档只负责横向检索、归类与跳转
- skill 不内置任何具体业务映射知识，只负责发现候选、交叉验证和生成结果

这一方案兼顾了：

- 人工阅读时的业务连续性
- AI 读取时的横向检索效率
- 长期维护时的信息一致性

## 14. 后续实现范围

第一版实现该 skill 时，至少需要覆盖以下能力：

- 解析结构化输入与自然语言输入
- 扫描 `docs/api`、`docs/superpowers/specs` 与代码事实
- 按主次文档规则执行新建或增量更新
- 对冲突和不确定项做统一输出
- 保证不在次文档复制主文档完整正文

第一版不要求覆盖所有功能范围，但至少要对以下 `scope` 形成稳定支持：

- `list`
- `create`
- `edit`
- `detail`

后续如需扩展到 `delete`、`import`、`export`、`audit`，只扩展章节和索引规则，不改变主次文档边界模型。

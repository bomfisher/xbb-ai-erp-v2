# 进销存系统工程结构与分层架构设计文档

## 1. 文档目的

本文档用于重新定义进销存系统在 P0 至后续演进阶段的项目工程结构、模块边界、纵向分层方式、横向依赖关系、行业扩展落位以及启动装配方式。本文档以现有 PRD 范围为基础，目标是形成一套可执行、可约束、可演进的工程架构方案，用于指导项目初始化、模块建设、代码评审和后续迭代。

本文档重点解决以下问题：

- 整个进销存系统应该划分哪些顶层 module。
- 单个业务 module 从 `controller` 到业务逻辑，再到数据库访问，应采用什么纵向结构。
- 业务与业务之间如何隔离，出现循环调用时应该如何抽取。
- 日志、消息、审批流等公共能力在系统中的位置是什么。
- 三个行业扩展在架构中的位置是什么，对通用模块的增强逻辑应落在何处。
- 项目应有几个启动类，移动端入口如何组织。
- 后续工程更新迭代必须遵守哪些规则。

## 2. 设计原则

### 2.1 模块化单体，不做表级拆分

当前阶段系统采用模块化单体作为主要工程形态。所谓模块化单体，是指物理部署可以保持较少的应用实例，但代码结构、依赖方向、业务边界必须按模块清晰隔离。模块边界按业务职责划分，不按数据库表划分，也不按前端菜单划分。

### 2.2 业务规则归模块，流程编排归应用层

每个业务模块对自身的核心规则负责，例如状态流转、价格命中、库存增减、核销规则、信用阻断规则等。这些规则必须留在该模块内部。跨模块业务动作允许发生，但跨模块只是流程协作，不意味着规则可以跨模块漂移。

### 2.3 跨模块调用只走 facade，不穿透实现

一个模块调用另一个模块时，只允许依赖对方暴露出来的 `facade` 契约，不允许直接调用对方的 `mapper`、持久化对象、内部 `service` 或数据库表。模块间协作依赖的是能力接口，不依赖实现细节。

### 2.4 技术公共能力与业务公共能力分离

日志、缓存、租户、安全、持久化等属于技术底座，应放在 `xbb-erp-base-*` 模块中。审批流、消息通知、价格中心、信用控制等属于业务公共能力，虽然被多个业务模块使用，但本质仍是业务模块，应放在 `xbb-erp-module-*` 中，而不是放进通用技术基础模块。

### 2.5 行业扩展通过扩展点增强，不直接污染核心模块

贸易/批发零售、制造业、互联网服务三类行业扩展必须建立在统一通用底座之上。行业扩展既可以新增独立业务模块，也可以增强已有核心模块。但增强逻辑必须通过预留扩展点进入，不允许在核心模块中大量散落 `if (industryType == ...)` 式分支逻辑。

## 4. 各类 module 的职责划分

## 4.1 技术底座模块 `xbb-erp-base-*`

### `xbb-erp-base-common`

存放通用异常、统一错误码、公共常量、通用工具、枚举基类、基础返回模型等最底层共性代码。该模块不得沉淀业务逻辑。

### `xbb-erp-base-web`

存放 Web 基础配置、统一异常处理、请求响应包装、参数绑定、接口幂等入口、控制器公共切面等能力。

### `xbb-erp-base-security`

存放登录认证、用户上下文、权限注解、鉴权过滤器、安全配置等能力。

### `xbb-erp-base-tenant`

存放租户上下文、`corpid` 解析、租户校验、租户过滤能力。所有核心业务模块均依赖此模块完成租户上下文接入。

### `xbb-erp-base-persistence`

存放 MyBatis 基础配置、分页插件、审计字段自动填充、持久化基类、Mapper 扫描配置、基础仓储组件等能力。

### `xbb-erp-base-cache`

存放 Redis 访问基础封装、缓存 Key 规范、分布式锁工具、幂等 Token 工具等能力。

### `xbb-erp-base-idgen`

存放技术主键生成与业务编码生成基础接口。具体业务单号规则不放在此模块，而由 `xbb-erp-module-code-rule` 负责。

### `xbb-erp-base-log`

存放 TraceId、统一日志上下文、操作日志基础能力、审计日志基础切面等技术能力。

### `xbb-erp-base-test`

存放测试基类、Testcontainers 配置、测试环境辅助工具、通用测试数据构造器等能力。

## 4.2 通用业务底座模块 `xbb-erp-module-*`

### 组织与基础主数据层

- `xbb-erp-module-org`：组织、部门、岗位、角色、数据权限。
- `xbb-erp-module-masterdata`：客户、供应商、仓库、结算对象等主数据。
- `xbb-erp-module-product`：SPU、SKU、分类、品牌、单位、商品控制属性。
- `xbb-erp-module-fund-account`：资金账户体系。
- `xbb-erp-module-contract`：合同对象、归属关系与业务引用约束。
- `xbb-erp-module-opening`：期初数据导入与基线建立，包括库存期初、往来期初、余额基线。

### 交易执行层

- `xbb-erp-module-purchase`：采购申请、采购订单、采购入库、采购退货、供应商对账来源。
- `xbb-erp-module-sales`：销售订单、销售出库、销售退货、客户对账来源。
- `xbb-erp-module-inventory`：库存事件、库存台账、锁库、冻结、盘点、调整、成本回写。

### 财务协同层

- `xbb-erp-module-receivable`：应收确认、余额承接、账龄基础。
- `xbb-erp-module-payable`：应付确认、余额承接、账龄基础。
- `xbb-erp-module-receipt`：收款、认领、核销、预收。
- `xbb-erp-module-payment`：付款、核销、预付。
- `xbb-erp-module-invoice`：发票申请、结果回写、红字处理。
- `xbb-erp-module-reconcile`：对账、对账差异处理。
- `xbb-erp-module-period-close`：期间锁定、结账、反结账。

### 平台能力层

- `xbb-erp-module-pricing`：标准价、协议价、价盘、价格命中。
- `xbb-erp-module-credit`：额度、账期、阻断、放行。
- `xbb-erp-module-approval`：审批模板、节点流转、放行控制。
- `xbb-erp-module-notification`：站内消息、待办、预警、跳转联动。
- `xbb-erp-module-file`：附件、打印模板、导出任务。
- `xbb-erp-module-code-rule`：对象编码与单据编号生成。
- `xbb-erp-module-settlement-rule`：结算方式规则。
- `xbb-erp-module-finance-policy`：确认时点、账龄规则、财务口径。
- `xbb-erp-module-bi`：指标口径、报表主题、数据钻取。
- `xbb-erp-module-workbench`：首页聚合、待办、预警、经营概览。

## 4.3 流程编排模块 `xbb-erp-process-*`

当多个核心模块之间出现明显的跨域流程编排需求时，不应让这些模块互相回调形成环，而应抽取为独立的流程编排模块。

- `xbb-erp-process-trade`：采购、销售、库存相关跨域流程编排。
- `xbb-erp-process-finance`：应收、应付、收付款、发票、结账相关跨域流程编排。
- `xbb-erp-process-support`：审批通过后的联动、消息触发、导出任务、异步补偿等支撑流程编排。

流程编排模块的职责是组织调用顺序、定义事务边界、控制同步与异步边界，不承载任何业务域内部的核心规则。

## 4.4 行业扩展模块 `xbb-erp-ext-*`

- `xbb-erp-ext-trade-retail`：贸易/批发零售扩展，如促销、零售差异流程、多仓履约差异。
- `xbb-erp-ext-manufacture`：制造业扩展，如 BOM、工单、领料、退料、补料、完工入库。
- `xbb-erp-ext-service`：互联网信息技术服务扩展，如服务合同、里程碑、验收、非实物履约。

行业扩展模块不是独立复制一套通用底座，而是在通用底座之上进行业务补强与新模块扩展。

## 4.5 启动装配模块 `xbb-erp-app-*`

推荐当前阶段使用 **3 个启动类 / 3 个装配模块**：

- `xbb-erp-app-admin`：PC 管理后台入口，同时承载后台管理类接口和内部业务 API。
- `xbb-erp-app-mobile`：移动端入口，负责移动端/BFF 风格接口、待办审批、轻量查询、消息处理。
- `xbb-erp-app-job`：定时任务、异步补偿、批处理、导出任务等后台执行入口。

三个启动类推荐分别命名为：

- `AdminApplication`
- `MobileApplication`
- `JobApplication`

移动端不是独立的一套业务系统，而是独立的一层访问入口。它与后台共用相同的业务模块、领域规则和数据库，只在控制器暴露、接口粒度和鉴权策略上有所区别。

### 5.0.1 细化 package 树说明

下面以 `xbb-erp-module-sales` 为例，对每一级 package 的推荐落位进一步展开，便于后续直接作为研发建包模板使用。

#### 1. `controller`

- 作用：协议接入层，负责接收不同来源的请求。
- 建议子包：`admin`、`mobile`、`open`。
- 建议类名：`SalesOrderAdminController`、`SalesTodoMobileController`、`OpenSalesOrderController`。
- 典型文件示例：
  - `controller/admin/SalesOrderAdminController.java`
  - `controller/mobile/SalesQueryMobileController.java`
  - `controller/open/OpenSalesStatusController.java`

#### 2. `app.command`

- 作用：定义写操作输入模型。
- 建议类名：`CreateSalesOrderCommand`、`SubmitSalesOrderCommand`、`SalesOutboundCommand`。
- 典型文件示例：
  - `app/command/CreateSalesOrderCommand.java`
  - `app/command/SalesOutboundCommand.java`

#### 3. `app.query`

- 作用：定义查询模型与查询服务。
- 建议类名：`SalesOrderListQuery`、`SalesOrderDetailQuery`、`SalesOrderQueryService`。
- 典型文件示例：
  - `app/query/SalesOrderListQuery.java`
  - `app/query/SalesOrderQueryService.java`

#### 4. `app.service`

- 作用：承担用例编排、事务边界、跨模块协作。
- 建议类名：`SalesOrderAppService`、`SalesOutboundAppService`、`SalesReturnAppService`。
- 典型文件示例：
  - `app/service/SalesOrderAppService.java`
  - `app/service/SalesOutboundAppService.java`

#### 5. `app.dto`

- 作用：承载应用层输出对象与聚合展示对象。
- 建议类名：`SalesOrderDTO`、`SalesOrderDetailDTO`、`SalesStatisticsDTO`。
- 典型文件示例：
  - `app/dto/SalesOrderDetailDTO.java`
  - `app/dto/SalesOutboundResultDTO.java`

#### 6. `app.assembler`

- 作用：负责请求对象、命令对象、DTO、响应对象之间的转换。
- 建议类名：`SalesOrderCommandAssembler`、`SalesOrderDTOAssembler`、`SalesOrderResponseAssembler`。
- 典型文件示例：
  - `app/assembler/SalesOrderCommandAssembler.java`
  - `app/assembler/SalesOrderResponseAssembler.java`

#### 7. `app.extension`

- 作用：定义应用层扩展点，承接行业增强或流程后处理。
- 建议类名：`BeforeSalesOrderCreateProcessor`、`AfterSalesOrderCreateProcessor`、`AfterSalesOutboundProcessor`。
- 典型文件示例：
  - `app/extension/BeforeSalesOrderCreateProcessor.java`
  - `app/extension/AfterSalesOutboundProcessor.java`

#### 8. `domain.model`

- 作用：定义聚合根、实体和核心业务对象。
- 建议类名：`SalesOrder`、`SalesOrderItem`、`SalesReturnOrder`、`SalesOutboundRecord`。
- 典型文件示例：
  - `domain/model/SalesOrder.java`
  - `domain/model/SalesOrderItem.java`

#### 9. `domain.valueobject`

- 作用：定义值对象，表达金额、地址、税率、客户快照等语义单元。
- 建议类名：`SalesOrderNo`、`CustomerSnapshot`、`MoneyAmount`、`TaxRate`。
- 典型文件示例：
  - `domain/valueobject/MoneyAmount.java`
  - `domain/valueobject/CustomerSnapshot.java`

#### 10. `domain.service`

- 作用：承载不适合放入单一聚合根的领域规则编排。
- 建议类名：`SalesOrderDomainService`、`SalesPricingDomainService`、`SalesCreditCheckDomainService`。
- 典型文件示例：
  - `domain/service/SalesOrderDomainService.java`
  - `domain/service/SalesPricingDomainService.java`

#### 11. `domain.policy`

- 作用：定义可替换的策略规则，例如定价、折扣、发货匹配。
- 建议类名：`SalesPricingPolicy`、`SalesDiscountPolicy`、`SalesDeliveryMatchPolicy`。
- 典型文件示例：
  - `domain/policy/SalesPricingPolicy.java`
  - `domain/policy/SalesDiscountPolicy.java`

#### 12. `domain.event`

- 作用：定义领域事件，表达关键业务事实。

### 5.0.2 建包时的落地规则

为避免后续模块演进过程中出现目录混乱，建议统一遵守以下规则：

- 如果一个类直接响应 HTTP 请求，只能放在 `controller`。
- 如果一个类承担业务用例编排，只能放在 `app.service`。
- 如果一个类定义业务规则、状态流转或领域语义，只能放在 `domain`。
- 如果一个类是给其他模块调用的正式入口，只能放在 `facade`。
- 如果一个类直接依赖数据库、缓存、MQ、外部接口等技术实现，只能放在 `infrastructure`。
- `query` 与 `command` 必须分开，读写语义不能混放。
- `PO`、`DTO`、`FacadeDTO`、`DomainModel` 不能混用同一个对象类。
- 行业增强优先通过 `app.extension` 或 `domain.extension` 接入，不允许直接修改大量核心主流程代码。

### 5.0.3 标准流程示例：以销售出库为例

下面给出一条符合本工程结构约束的标准调用链，帮助研发人员理解“什么代码应该落在哪一层”。

```text
SalesOutboundAdminController
    -> SalesOutboundAppService
        -> SalesOrderRepository.load(orderId)
        -> SalesOrderDomainService.checkCanOutbound(order)
        -> CreditFacade.checkCredit(command)
        -> InventoryFacade.outbound(command)
        -> ReceivableFacade.createReceivable(command)
        -> SalesOrderDomainService.markOutbound(order, result)
        -> SalesOrderRepository.save(order)
        -> AfterSalesOutboundProcessor.execute(...)
        -> SalesOrderEventProducer.send(...)
```

按层拆解后，各层职责如下：

- `controller`：接收销售出库请求，完成参数绑定与基础校验。
- `app.service`：组织整条出库流程，定义事务边界，串联库存、信用、应收等协作模块。
- `domain.service`：判断销售单是否允许出库，出库后状态应如何变化。
- `facade`：库存、信用、应收模块以稳定接口形式被调用。
- `repository`：负责装载和保存销售聚合根。
- `extension`：承接行业扩展的出库后处理动作。
- `mq`：负责异步事件发送，而不是在控制器或领域模型中直接发消息。

推荐的示意代码结构如下：

```java
@PostMapping("/outbound")
public Result<Void> outbound(@RequestBody SalesOutboundRequest request) {
    SalesOutboundCommand command = salesOrderCommandAssembler.toOutboundCommand(request);
    salesOutboundAppService.outbound(command);
    return Result.success();
}
```

```java
@Transactional
public void outbound(SalesOutboundCommand command) {
    SalesOrder order = salesOrderRepository.loadById(command.orderId());

    salesOrderDomainService.checkCanOutbound(order, command);
    creditFacade.checkCredit(...);
    InventoryOutboundFacadeResult result = inventoryFacade.outbound(...);
    receivableFacade.createReceivable(...);

    salesOrderDomainService.markOutbound(order, result, command);
    salesOrderRepository.save(order);

    afterSalesOutboundProcessor.execute(order, command, result);
    salesOrderEventProducer.send(new SalesOrderOutboundEvent(...));
}
```

这类示例的核心价值在于统一团队的直觉：

- 控制器不碰数据库。
- 应用层负责流程，不负责定义底层业务规则。
- 领域层不直接访问 HTTP、Redis、MQ、第三方接口。
- 外部模块能力必须通过 `facade` 进入。

### 5.0.4 反面示例：哪些代码属于放错层

下面列出几个最常见的错误落位方式，后续代码评审应重点拦截。

#### 反例 1：在 `controller` 中直接写业务判断

错误示例：

```java
@PostMapping("/submit")
public Result<Void> submit(@RequestBody SalesOrderRequest request) {
    SalesOrderPO po = salesOrderMapper.selectById(request.getId());
    if (!"DRAFT".equals(po.getStatus())) {
        throw new BizException("当前状态不允许提交");
    }
    salesOrderMapper.updateStatus(request.getId(), "SUBMITTED");
    return Result.success();
}
```

问题：

- 把业务状态规则写进了入口层。
- 控制器直接操作 `mapper`，破坏模块分层。
- 后续移动端、开放接口、批处理入口无法复用这段规则。

正确做法：

- 控制器只接请求。
- 状态判断放入 `domain`。
- 持久化更新通过 `app.service -> repository` 完成。

#### 反例 2：在 `app.service` 中堆满规则细节

错误示例：

```java
@Transactional
public void create(CreateSalesOrderCommand command) {
    if (command.items().isEmpty()) {
        throw new BizException("明细不能为空");
    }
    if (command.totalAmount().compareTo(BigDecimal.ZERO) <= 0) {
        throw new BizException("金额必须大于 0");
    }
    if (!customerRemoteClient.isValid(command.customerId())) {
        throw new BizException("客户无效");
    }
    ...
}
```

问题：

- 应用层逐渐膨胀成“万能业务层”。
- 规则无法沉淀为稳定领域能力。
- 同类规则在其他流程中容易重复编写。

正确做法：

- 输入合法性与领域规则放入 `domain.service` 或 `domain.model`。
- 应用层保留流程组织与事务边界职责。

#### 反例 3：跨模块直接调用别人的 `mapper`

错误示例：

```java
inventoryMapper.lockStock(...);
receivableMapper.insert(...);
```

问题：

- 模块边界直接失效。
- 以后库存模块、应收模块内部重构时，调用方会全部被牵连。
- 编译期形成隐式强耦合，最终导致环依赖。

正确做法：

- 统一改为 `inventoryFacade.lockStock(...)`
- 统一改为 `receivableFacade.createReceivable(...)`

#### 反例 4：把行业差异写成大量 `if-else`

错误示例：

```java
if (industryType == MANUFACTURE) {
    // 制造业校验
} else if (industryType == TRADE) {
    // 贸易行业校验
} else if (industryType == SERVICE) {
    // 服务行业校验
}
```

问题：

- 核心模块会越来越重。
- 行业逻辑污染通用底座。
- 新增一个行业时需要持续改核心流程。

正确做法：

- 在 `app.extension` 或 `domain.extension` 预留扩展点。
- 各行业模块实现自己的扩展逻辑。

#### 反例 5：把同一个对象同时当作 `PO`、`DTO`、领域对象使用

问题：

- 数据库存储结构与业务语义强耦合。
- 页面返回字段、持久化字段、领域行为互相污染。
- 一个字段改动会联动冲击多个层次。

正确做法：

- `PO` 只用于持久化。
- `DTO` 只用于应用层或接口层传输。
- `DomainModel` 只用于承载业务语义与行为。

### 5.0.5 package 与类命名统一规范

为保证整个进销存系统在多个模块同时演进时仍然具备一致性，建议统一采用以下命名规范。

#### 1. package 命名规范

- 全部使用小写英文单词。
- package 名称应表达职责，不表达技术时态。
- 统一使用固定层次：`controller`、`app`、`domain`、`facade`、`infrastructure`。
- 不使用含糊命名，如 `utils2`、`serviceimpl`、`commonbiz`、`temp`。

推荐示例：

- `com.xxx.is.sales.controller.admin`
- `com.xxx.is.sales.app.service`
- `com.xxx.is.sales.domain.model`
- `com.xxx.is.sales.infrastructure.persistence.mapper`

不推荐示例：

- `com.xxx.is.sales.serviceImpl`
- `com.xxx.is.sales.common`
- `com.xxx.is.sales.utils`
- `com.xxx.is.sales.mix`

#### 2. Controller 命名规范

- 后台接口：`业务名 + AdminController`
- 移动端接口：`业务名 + MobileController`
- 开放接口：`Open + 业务名 + Controller`

示例：

- `SalesOrderAdminController`
- `SalesQueryMobileController`
- `OpenSalesOrderController`

#### 3. Command / Query 命名规范

- 写操作输入：`动作 + 业务对象 + Command`
- 查询输入：`业务对象 + Query` 或 `业务对象 + 场景 + Query`

示例：

- `CreateSalesOrderCommand`
- `SubmitSalesOrderCommand`
- `SalesOrderListQuery`
- `SalesDashboardQuery`

#### 4. AppService 命名规范

- 按业务动作组织时：`业务动作 + AppService`
- 按聚合入口组织时：`业务对象 + AppService`

示例：

- `SalesOrderAppService`
- `SalesOutboundAppService`
- `SalesReturnAppService`

如果一个类已经过大，应拆成多个动作型 `AppService`，不要继续往单个 `SalesService` 中堆逻辑。

#### 5. DomainModel 命名规范

- 聚合根、实体使用清晰业务名词。
- 不在领域模型名中带 `PO`、`DTO`、`Entity`、`VO` 这类技术后缀。

推荐示例：

- `SalesOrder`
- `SalesOrderItem`
- `SalesReturnOrder`

不推荐示例：

- `SalesOrderEntity`
- `SalesOrderDTO`
- `SalesOrderPO`

#### 6. Repository 命名规范

- 领域仓储接口：`业务对象 + Repository`
- 基础设施实现：`业务对象 + RepositoryImpl`

示例：

- `SalesOrderRepository`
- `SalesOrderRepositoryImpl`

#### 7. Facade 命名规范

- 模块对外能力统一使用：`业务域 + Facade`
- 不建议使用含糊命名如 `SalesServiceFacade`、`SalesManagerFacade`

示例：

- `SalesFacade`
- `InventoryFacade`
- `ReceivableFacade`

#### 8. 持久化对象命名规范

- 主表对象：`业务对象 + PO`
- 明细表对象：`业务对象明细 + PO`
- Mapper：`业务对象 + Mapper`
- Convertor：`业务对象 + Convertor`

示例：

- `SalesOrderPO`
- `SalesOrderItemPO`
- `SalesOrderMapper`
- `SalesOrderConvertor`

#### 9. 事件与扩展点命名规范

- 领域事件：`业务事实 + Event`
- 应用层处理器：`动作阶段 + Processor`
- 领域扩展点：`业务动作 + Extension`

示例：

- `SalesOrderCreatedEvent`
- `AfterSalesOutboundProcessor`
- `SalesSubmitValidateExtension`

#### 10. 命名治理规则

- 类名优先表达业务含义，不优先表达框架实现。
- 一个名字只表达一个职责，不同时承载“查询 + 写入 + 同步 + 导出”多种语义。
- 名称一旦确定，应在同层模块保持一致，不允许销售模块叫 `AppService`，采购模块改叫 `BizService`。
- 后续新增模块时，优先复制标准命名模板，不重新发明术语。

### 5.0.6 测试分层规范

为了保证工程结构不是“设计上分层，测试上混乱”，建议业务模块测试也按相同的分层思路建设。测试目标不是只验证接口能通，而是验证每一层承担的职责是否正确。

#### 1. 测试分层总原则

- 领域规则优先通过领域层测试覆盖。
- 应用编排优先通过应用层集成测试覆盖。
- 跨模块协作优先通过模块协同测试覆盖。
- 控制器测试只验证协议适配、参数绑定、权限与返回结构，不承担业务主验证职责。
- 不允许把所有验证都压到接口联调阶段才发现问题。

推荐的测试分层如下：

```text
domain test        -> 验证业务规则、状态流转、领域约束
app integration    -> 验证用例编排、事务边界、跨模块 facade 协作
controller test    -> 验证入参、鉴权、返回结构、错误码
repository test    -> 验证持久化映射、查询条件、数据装载正确性
module flow test   -> 验证采购/销售/库存/财务等跨模块链路
```

#### 2. `domain` 层测试

目标：验证本模块最核心的业务规则。

建议放置位置示例：

- `src/test/java/com/xxx/is/sales/domain/model/SalesOrderTest.java`
- `src/test/java/com/xxx/is/sales/domain/service/SalesOrderDomainServiceTest.java`
- `src/test/java/com/xxx/is/sales/domain/policy/SalesPricingPolicyTest.java`

重点覆盖内容：

- 状态是否允许流转。
- 数量、金额、税率、折扣等规则是否正确。
- 全量/部分出库、全量/部分退货等边界条件。
- 非法输入是否按预期抛出业务异常。

测试命名建议：

- `should_mark_partially_outbound_when_only_part_of_items_are_shipped`
- `should_reject_submit_when_order_status_is_not_draft`

这类测试不应依赖 Controller、Mapper、Redis、MQ。它们应尽量保持轻量，聚焦业务真规则。

#### 3. `app` 层测试

目标：验证用例编排是否正确，特别是事务边界与跨模块调用顺序。

建议放置位置示例：

- `src/test/java/com/xxx/is/sales/app/service/SalesOutboundAppServiceTest.java`
- `src/test/java/com/xxx/is/sales/app/service/SalesOrderAppServiceIntegrationTest.java`

重点覆盖内容：

- 一个完整业务动作是否按预期组织执行。
- 是否正确调用了库存、信用、应收等 `facade`。
- 出错时事务是否回滚。
- 成功后领域对象是否被正确保存。
- 扩展点处理器是否在正确阶段执行。

这层测试可以适度依赖 Spring 容器、事务和仓储实现，但不要退化成只测 Controller HTTP 通路。

#### 4. `controller` 层测试

目标：验证协议层是否正确适配，而不是重测业务规则。

建议放置位置示例：

- `src/test/java/com/xxx/is/sales/controller/admin/SalesOrderAdminControllerTest.java`
- `src/test/java/com/xxx/is/sales/controller/mobile/SalesQueryMobileControllerTest.java`

重点覆盖内容：

- 参数绑定是否正确。
- 必填项缺失时是否返回正确错误。
- 鉴权、租户上下文、权限控制是否生效。
- 返回结构、分页结构、错误码是否符合约定。

不要在这里堆过多业务分支断言，否则会把领域测试和应用测试的责任挤压到接口层。

#### 5. `repository / persistence` 层测试

目标：验证数据库映射与仓储装载行为。

建议放置位置示例：

- `src/test/java/com/xxx/is/sales/infrastructure/persistence/repository/SalesOrderRepositoryImplTest.java`
- `src/test/java/com/xxx/is/sales/infrastructure/persistence/mapper/SalesStatisticsMapperTest.java`

重点覆盖内容：

- `PO` 与领域对象转换是否正确。
- 查询条件是否符合预期。
- 聚合根保存后是否能正确回读。
- 复杂统计 SQL 是否返回正确结果。

这一层建议结合真实数据库环境或容器化数据库测试，不建议只依赖纯 mock 验证 SQL 行为。

#### 6. 跨模块协同测试

目标：验证多个模块通过 `facade` 连接后的完整主流程。

建议放置位置示例：

- `src/test/java/com/xxx/is/process/trade/SalesOutboundTradeProcessTest.java`
- `src/test/java/com/xxx/is/process/finance/ReceiptWriteOffProcessTest.java`

重点覆盖内容：

- 销售出库后库存是否减少。
- 销售出库后应收是否生成。
- 采购入库后应付是否生成。
- 审批通过后通知、后处理、事件是否触发。

这类测试不是为了覆盖所有边界，而是为了覆盖关键跨模块主链路，防止模块间契约漂移。

#### 7. 测试命名与分类建议

建议统一命名：

- 领域层：`*Test`
- Spring 集成：`*IntegrationTest`
- 跨模块流程：`*ProcessTest`
- Mapper / 仓储：`*RepositoryImplTest`、`*MapperTest`

建议统一目录归属：

- 领域测试跟随 `domain` 目录结构。
- 应用测试跟随 `app` 目录结构。
- 持久化测试跟随 `infrastructure` 目录结构。
- 流程测试优先放在 `xbb-erp-process-*` 模块中。

#### 8. 测试建设约束

- 不允许把本应在 `domain` 覆盖的规则只放到接口联调验证。
- 不允许跨模块直接 mock 对方 `mapper` 进行伪联调。
- 不允许所有测试都写成超大一体化“从 HTTP 到数据库”的慢测试。
- 不允许因为测试难写，就把业务规则继续堆到 `app.service` 或 `controller`。

### 5.0.7 新增一个业务 module 的标准落地步骤

为了保证后续模块持续新增时，工程结构仍然稳定，建议每新增一个业务模块都按以下顺序推进，而不是想到哪里写到哪里。

#### 第 1 步：确认模块边界

在建模块前先回答四个问题：

- 这个模块的核心业务对象是什么。
- 这个模块拥有哪些状态与规则。
- 这个模块对外要暴露哪些能力。
- 这个模块依赖哪些已有模块的 `facade`。

如果这些问题答不清，说明模块边界还没收敛，不应急着建包。

#### 第 2 步：创建顶层工程 module

例如新增“调拨模块”，应先创建：

- `xbb-erp-module-transfer`

并在父工程中纳入统一依赖管理、统一扫描范围、统一代码规范约束。

#### 第 3 步：创建标准主干 package

优先建立主干目录，而不是先建一堆零散类：

```text
com.xxx.is.transfer
├── controller
├── app
├── domain
├── facade
└── infrastructure
```

如果当前阶段功能很小，也建议至少保留这 5 个一级目录，确保后续扩展时不用重新搬家。

#### 第 4 步：先定义 `domain.model` 与 `domain.repository`

新增模块时，不建议从 Controller 开始写。更好的顺序是：

1. 定义核心聚合根。
2. 定义核心状态与行为。
3. 定义仓储接口。
4. 明确业务规则放在 `domain.model` 还是 `domain.service`。

这一步的目标是先把“业务本体”立住，而不是先把接口跑通。

#### 第 5 步：再定义 `app.command`、`app.service`

当领域对象明确后，再开始定义：

- 这个模块有哪些业务动作。
- 每个动作对应什么 `Command`。
- 哪些动作由哪个 `AppService` 编排。
- 哪些动作需要事务。
- 哪些动作需要调用别的模块 `facade`。

这一步会把“领域规则”和“用例流程”分开，避免后期所有逻辑都堆在一个 Service 里。

#### 第 6 步：定义 `facade`

如果该模块需要被外部调用，就必须在早期明确：

- 对外暴露哪些能力。
- 输入输出契约是什么。
- 哪些内部实现绝不能透出。

推荐先写接口，再写实现：

- `TransferFacade`
- `TransferFacadeImpl`
- `facade/dto/*`

#### 第 7 步：最后落地 `infrastructure`

当领域接口和应用流程都明确后，再实现：

- `PO`
- `Mapper`
- `RepositoryImpl`
- `Convertor`
- `Cache`
- `Integration`
- `MQ`

这样可以避免一上来围着表结构写代码，最后发现领域结构根本不稳定。

#### 第 8 步：补齐 `controller`

业务主干清楚后，再开放入口：

- 后台入口：`controller.admin`
- 移动端入口：`controller.mobile`
- 开放接口入口：`controller.open`

控制器只负责接入，不承担模块设计职责。

#### 第 9 步：补齐最小测试集

一个新模块至少应同时补齐以下三类测试：

- 1 个核心领域规则测试。
- 1 个核心应用流程测试。
- 1 个核心仓储/持久化测试。

如果该模块会被其他模块协同调用，还应补 1 个 `facade` 级联调测试或流程测试。

#### 第 10 步：最后再补扩展点

如果模块存在明显行业差异，最后再评估是否要预留：

- `app.extension`
- `domain.extension`

不要在模块刚创建时过度设计所有扩展点，但只要已经确认未来一定存在行业分支，就应在主流程稳定节点预留插点，而不是将来靠 `if-else` 硬插进去。

#### 第 11 步：新增 module 的交付检查清单

建议每个新增模块上线前都检查以下内容：

- 是否已经建立独立 module，而不是把新业务塞进旧模块。
- 是否已经区分 `controller/app/domain/facade/infrastructure`。
- 是否已经定义对外 `facade`，而不是允许别人直接调 `mapper`。
- 是否已经建立仓储接口与实现分离。
- 是否已经补齐最小测试集。
- 是否已经明确该模块是否需要行业扩展点。
- 是否已经明确它在依赖图中的位置，不会与现有模块形成环依赖。

### 5.0.8 跨 module 调用规范

随着模块数量增加，系统最容易失控的地方不是单模块内部，而是模块之间如何协作。因此，跨模块调用必须建立统一规则，避免逐步演化成“所有模块互相直连”的网状耦合结构。

#### 1. 跨模块调用总原则

跨模块协作统一遵循以下判断顺序：

- 如果只是调用另一个模块已经稳定暴露的业务能力，优先调用对方 `facade`。
- 如果一个流程需要串联多个模块，且存在明确主导业务方，由主导模块的 `app.service` 负责编排。
- 如果一个流程横跨多个模块，且不存在明显主导模块，或者已经出现循环依赖倾向，则抽取到 `xbb-erp-process-*`。
- 如果后置动作不要求强一致，则优先改为事件驱动，而不是继续同步级联调用。

可以把这套判断简化为：

```text
单点能力复用       -> facade
主导模块发起流程   -> 发起方 app.service
跨域长流程编排     -> xbb-erp-process-*
非强一致后置动作   -> event
```

#### 2. 什么情况下应该调用 `facade`

适用条件：

- 你要调用的是另一个模块已经沉淀好的稳定能力。
- 该能力边界清晰，输入输出可稳定定义。
- 这个动作仍然属于当前模块主导流程的一部分。

典型示例：

- 销售模块调用 `InventoryFacade.outbound()`。
- 销售模块调用 `ReceivableFacade.createReceivable()`。
- 采购模块调用 `PayableFacade.createPayable()`。
- 任意业务模块调用 `ApprovalFacade.submit()`。

推荐结构：

```text
SalesOutboundAppService
    -> InventoryFacade
    -> CreditFacade
    -> ReceivableFacade
```

不推荐结构：

```text
SalesOutboundAppService
    -> InventoryMapper
    -> ReceivableMapper
```

判断标准：

- 当前模块是否仍然是主业务方。
- 被调用方是否只是提供能力，而不是反过来主导流程。
- 调用结束后是否仍由当前模块决定主流程是否完成。

如果答案是“是”，通常应该继续使用 `facade`。

#### 3. 什么情况下应该抽取 `xbb-erp-process-*`

适用条件：

- 一个流程需要同时编排多个业务模块。
- 流程跨越交易域、财务域、审批域、通知域等多个域。
- 没有任何一个业务模块天然适合长期承担这个全局流程。
- 如果继续放在某个业务模块中，会导致它越来越像“总调度中心”。

典型场景：

- 月结、反结账、结账回滚。
- 审批通过后的多模块联动。
- 销售出库、开票、收款、核销之间的复合长流程。
- 制造业的工单完工后，联动库存、成本、财务确认等流程。

推荐结构：

```text
xbb-erp-process-finance
    -> ReceivableFacade
    -> ReceiptFacade
    -> InvoiceFacade
    -> ReconcileFacade
    -> PeriodCloseFacade
```

```text
xbb-erp-process-trade
    -> SalesFacade
    -> InventoryFacade
    -> PricingFacade
    -> CreditFacade
```

抽取 `xbb-erp-process-*` 的核心目的，不是再造一个“大而全业务模块”，而是：

- 让主流程编排与单模块业务规则分离。
- 避免把多个领域规则混进某一个业务模块。
- 避免 A 调 B，B 调 C，C 又反向调 A 的结构出现。

#### 4. 什么情况下应该使用事件

适用条件：

- 当前动作完成后，需要通知其他模块做后置处理。
- 后置动作不要求与主事务强一致。
- 即使后置动作稍后完成，也不会破坏核心业务正确性。
- 你希望降低同步依赖深度，减少长链路阻塞。

典型场景：

- 销售出库完成后，异步推送 BI 指标。
- 审批通过后，异步发送站内消息、短信、待办提醒。
- 单据变更后，异步生成审计日志、订阅通知。
- 行业扩展中的保存后补充动作，不要求主事务内强一致完成。

推荐结构：

```text
SalesOutboundAppService
    -> SalesOrderRepository.save(...)
    -> publish SalesOrderOutboundEvent

NotificationConsumer
    -> NotificationFacade.send(...)

BiConsumer
    -> BiFacade.recordMetric(...)
```

事件方式的关键边界是：

- 事件表达“事实已经发生”，不是“请求你帮我做决定”。
- 主流程成功与否，不能依赖异步消费者是否马上处理成功。
- 如果主流程必须等某动作成功后才能提交事务，就不应改成纯事件模式。

#### 5. `facade`、`process`、`event` 的选型对照

| 场景                                | 推荐方式                       | 原因                   |
| ----------------------------------- | ------------------------------ | ---------------------- |
| 当前模块主导，调用外部稳定能力      | `facade`                       | 简单直接，边界清晰     |
| 多模块长链路编排，无明确长期主导方  | `xbb-erp-process-*`            | 降低主业务模块膨胀     |
| 后置通知、统计、补偿、预警          | `event`                        | 降低同步耦合与链路阻塞 |
| 当前模块主导，但涉及 2~3 个支撑能力 | `app.service + facade`         | 不必过早抽流程模块     |
| 已经出现 A -> B -> C -> A 倾向      | `xbb-erp-process-*` 或 `event` | 必须打断环依赖趋势     |

#### 6. 跨模块调用禁止事项

后续研发必须禁止以下写法：

- 跨模块直接调用 `mapper`。
- 跨模块直接依赖对方 `PO`。
- 在 `domain` 中直接调用其他模块实现类。
- 因为“只是一个简单需求”就在 Controller 里临时串别的模块。
- 用事件替代所有事情，导致本应强一致的主流程被拆散。
- 把 `xbb-erp-process-*` 写成第二套业务域，把所有规则都搬进去。

#### 7. 跨模块调用评审检查点

每次新增跨模块协作代码时，建议至少检查以下问题：

- 当前主导模块是谁。
- 被调用方暴露的是 `facade` 还是内部实现。
- 这次调用是否可能导致未来形成反向依赖。
- 这是不是一个应抽 `xbb-erp-process-*` 的信号。
- 这个后置动作是否可以改为事件驱动。
- 如果失败，事务边界该落在哪一层。

### 5.0.9 行业扩展落地模板

行业扩展不是“在通用模块里到处加行业判断”，而是“在通用底座稳定的前提下，通过扩展点承接行业差异”。为了让后续贸易、制造、互联网服务三个行业都能稳定演进，建议统一采用以下落地模板。

#### 1. 行业扩展总原则

行业扩展统一遵循以下原则：

- 通用共性优先留在核心模块。
- 行业差异优先放在 `xbb-erp-ext-*`。
- 增强核心流程时，优先使用扩展点，不直接散落 `if (industryType)`。
- 行业新增字段优先扩展表，不直接污染主表。
- 后置行业流程优先在稳定节点后挂接，不打断主业务抽象。

#### 2. 行业扩展的三种常见类型

##### 类型一：新增行业专属业务模块

适用场景：

- 制造业新增 `BOM`、`工单`、`领料`、`完工入库`。
- 服务行业新增 `里程碑验收单`、`服务履约单`。

建议落位：

- `xbb-erp-ext-manufacture`
- `xbb-erp-ext-service`

并在扩展模块内部继续遵循标准结构：

```text
xbb-erp-ext-manufacture
└── src/main/java/com/xxx/is/ext/manufacture
    ├── controller
    ├── app
    ├── domain
    ├── facade
    └── infrastructure
```

##### 类型二：增强通用模块的字段

适用场景：

- 制造业采购单额外记录加工单号。
- 零售行业销售单额外记录促销活动编码。
- 服务行业销售单额外记录项目阶段。

推荐方式：

- 通用字段进入核心主表。
- 行业专属字段进入扩展表。

示例：

```text
sales_order                // 通用主表
sales_order_ext_trade      // 贸易行业扩展表
sales_order_ext_mf         // 制造行业扩展表
sales_order_ext_service    // 服务行业扩展表
```

推荐对象结构：

- 核心模块：`SalesOrder`、`SalesOrderPO`
- 行业扩展：`TradeSalesOrderExt`、`ManufactureSalesOrderExtPO`

这样做的好处是：

- 主表保持稳定。
- 行业字段只影响自身扩展模块。
- 后续某行业字段若沉淀为通用能力，再评估是否升级进主模型。

##### 类型三：增强保存前校验或保存后流程

适用场景：

- 制造业要求销售出库前必须校验生产批次。
- 零售行业要求销售保存时校验促销资格。
- 服务行业要求订单审批通过后自动生成里程碑任务。

这类增强不应直接改写核心主流程，而应接入标准扩展点。

#### 3. 保存前校验的落地模板

建议在核心模块预留领域或应用扩展点，例如：

```text
app/extension/BeforeSalesOrderCreateProcessor.java
domain/extension/SalesSubmitValidateExtension.java
```

核心模块主流程：

```java
public void create(CreateSalesOrderCommand command) {
    beforeSalesOrderCreateProcessor.execute(command);
    salesOrderDomainService.checkCreateRule(command);
    ...
}
```

制造行业扩展实现：

```java
@Component
public class ManufactureBeforeSalesOrderCreateProcessor implements BeforeSalesOrderCreateProcessor {
    @Override
    public void execute(CreateSalesOrderCommand command) {
        // 制造业特有校验
    }
}
```

推荐落位：

- 核心接口：`xbb-erp-module-sales/app/extension`
- 行业实现：`xbb-erp-ext-manufacture/.../extension`

这样可以保证：

- 主流程仍由核心模块控制。
- 行业校验逻辑不污染核心领域类。
- 不同行业可以各自注册自己的处理器实现。

#### 4. 保存后业务流程的落地模板

如果行业增强发生在保存后，应先判断是否要求强一致。

##### 4.1 要求强一致

如果保存成功后，必须立即完成后续动作才能算业务成功，则应采用应用层后处理器。

示例：

```text
app/extension/AfterSalesOrderCreateProcessor.java
app/extension/AfterSalesOutboundProcessor.java
```

核心流程：

```java
salesOrderRepository.save(order);
afterSalesOrderCreateProcessor.execute(order, command);
```

##### 4.2 不要求强一致

如果只是通知、统计、衍生任务生成等动作，则应采用事件方式。

示例：

```java
salesOrderEventProducer.send(new SalesOrderCreatedEvent(...));
```

扩展模块消费者：

```java
@Component
public class ServiceSalesOrderCreatedConsumer {
    public void handle(SalesOrderCreatedEvent event) {
        // 生成服务里程碑任务
    }
}
```

#### 5. 行业扩展 package 建议模板

以“制造业对销售模块增强”为例，推荐如下结构：

```text
xbb-erp-ext-manufacture
└── src/main/java/com/xxx/is/ext/manufacture/sales
    ├── extension
    │   ├── ManufactureBeforeSalesOrderCreateProcessor.java
    │   ├── ManufactureSalesSubmitValidateExtension.java
    │   └── ManufactureAfterSalesOutboundProcessor.java
    ├── domain
    │   ├── model
    │   │   └── ManufactureSalesOrderExt.java
    │   └── service
    │       └── ManufactureSalesRuleService.java
    └── infrastructure
        └── persistence
            ├── po
            │   └── ManufactureSalesOrderExtPO.java
            ├── mapper
            │   └── ManufactureSalesOrderExtMapper.java
            └── repository
                └── ManufactureSalesOrderExtRepository.java
```

这个结构强调两点：

- 核心销售模块不直接变成“制造版销售模块”。
- 行业扩展有自己的模型、规则和持久化实现。

#### 6. 行业扩展实施顺序建议

新增一个行业增强需求时，建议按以下顺序判断：

1. 这是不是所有行业共用能力。
2. 如果不是，是否只属于某个行业。
3. 如果只属于某个行业，是字段差异、规则差异，还是流程差异。
4. 字段差异优先扩展表。
5. 规则差异优先 `domain.extension`。
6. 流程差异优先 `app.extension` 或事件。
7. 如果已经形成新的完整业务域，则单独建设行业业务模块。

#### 7. 行业扩展禁止事项

- 不允许在核心模块主流程中大量写 `if (industryType)`。
- 不允许行业扩展直接改写核心模块 `mapper`。
- 不允许行业专属字段无评估直接进入所有通用主表。
- 不允许为了赶需求，把行业逻辑直接塞到 `app.service` 临时分支里长期保留。
- 不允许核心模块在编译期反向依赖 `xbb-erp-ext-*`。

#### 8. 行业扩展评审检查点

每次新增行业增强时，建议至少检查：

- 这是字段扩展、规则扩展，还是流程扩展。
- 是否已经使用扩展点，而不是直接污染核心流程。
- 是否需要扩展表，而不是直接改主表。
- 是否已经把行业逻辑封装在 `xbb-erp-ext-*` 内部。
- 是否会导致核心模块反向依赖扩展模块。
- 是否存在未来第二个行业也会用到的潜在通用能力。

### 5.0.10 module 间出现循环依赖时的处理方式

随着业务模块不断增加，模块之间一定会出现越来越多的协作关系。真正危险的不是“模块之间有调用”，而是“模块之间开始互相依赖，最后形成环”。一旦环依赖出现，系统会逐步失去可维护性，具体表现为：

- 任意一个模块修改，都会牵动多个模块一起改。
- 单模块无法独立测试，联调成本越来越高。
- 依赖链越来越长，最终出现 A 调 B，B 调 C，C 又反向调 A。
- 某个模块本来只应该维护本域规则，最后却逐步变成跨多个域的流程总控。

因此，循环依赖不是“编码小问题”，而是架构边界已经开始失稳的明确信号。一旦发现，优先处理结构，而不是继续堆业务代码。

#### 1. 什么叫 module 间循环依赖

典型循环依赖不是 Maven 物理模块一定已经互相 `dependency`，而是业务代码层已经形成相互回调趋势，例如：

- `sales` 调 `inventory`
- `inventory` 又调 `receivable`
- `receivable` 又反过来调 `sales`

这类结构的本质是：

- 模块已经不再只关心自己的领域规则。
- 流程责任在多个模块之间来回漂移。
- 最终没有任何一个清晰的主导者。

#### 2. 循环依赖出现前的错误结构图

下面是一种典型的错误演进方式：

```text
销售出库主流程（错误示意）

SalesAppService
    -> InventoryFacade
           -> ReceivableFacade
                  -> SalesFacade
```

如果把它画成模块关系图，会变成：

```text
┌───────────────┐
│ xbb-erp-module-sales │
└──────┬────────┘
       │ 调用
       v
┌──────────────────┐
│ xbb-erp-module-inventory │
└──────┬─────────────┘
       │ 调用
       v
┌──────────────────┐
│ xbb-erp-module-receivable │
└──────┬─────────────┘
       │ 反向调用
       v
┌───────────────┐
│ xbb-erp-module-sales │
└───────────────┘
```

这就是一个标准闭环：

```text
sales -> inventory -> receivable -> sales
```

这种结构的直接问题是：

- `sales` 是否完成，变成要等 `inventory`、`receivable` 内部再回调回来。
- `inventory` 不再只是库存域，而被迫理解应收与销售流程。
- `receivable` 本应只关心应收确认，却开始反向影响销售状态。

#### 3. 为什么这种结构会出现

循环依赖通常不是一开始就设计出来的，而是需求逐步叠加后自然长出来的：

- 第一次需求：销售出库时扣库存，于是 `sales -> inventory`。
- 第二次需求：库存扣减后要生成应收，于是 `inventory -> receivable`。
- 第三次需求：应收生成后要回写销售单财务状态，于是 `receivable -> sales`。

每一步单看都像“顺手加一行调用”，但三次叠加后就形成了结构性问题。

所以后续代码评审时，不能只问“这一行调用对不对”，还要问：

- 这次调用会不会让模块承担不属于自己的流程责任。
- 这次调用会不会形成未来反向依赖的起点。

#### 4. 正确处理方式一：由主导模块统一收口编排

如果一个流程存在明确主导业务方，优先做法不是抽新模块，而是把编排责任收回主导模块的 `app.service`，其他模块只提供能力。

以销售出库为例，主导方显然是 `sales`，因此推荐改造成：

```text
SalesOutboundAppService
    -> InventoryFacade.outbound()
    -> ReceivableFacade.createReceivable()
    -> SalesOrderDomainService.markOutboundResult()
```

改造后的结构图：

```text
┌───────────────┐
│ xbb-erp-module-sales │
└───┬─────┬─────┘
    │     │
    │     └─────────────────────┐
    │                           │
    v                           v
┌──────────────────┐     ┌──────────────────┐
│ xbb-erp-module-inventory │     │ xbb-erp-module-receivable │
└──────────────────┘     └──────────────────┘
```

这里的关键变化是：

- `sales` 作为主导模块，自己决定流程顺序。
- `inventory` 只负责库存扣减。
- `receivable` 只负责应收生成。
- `inventory` 与 `receivable` 不再互相调用，也不再反向调 `sales`。

这种结构适用于：

- 当前流程主导模块很清晰。
- 被调用模块只是支撑能力模块。
- 主流程长度还可控，没有复杂的跨域状态机。

#### 5. 正确处理方式二：抽取 `xbb-erp-process-*` 作为流程编排层

如果一个流程已经跨越多个模块，并且不存在明显适合长期承载的主业务方，就不应继续让某个业务模块越长越大，而应抽取 `xbb-erp-process-*`。

例如：

- 审批通过后联动销售、库存、应收、通知。
- 月结时联动库存、应收、应付、发票、结账。
- 制造完工后联动库存、成本、财务确认、消息提醒。

错误结构可能是：

```text
A -> B -> C -> D -> A
```

改造后应变为：

```text
ProcessAppService
    -> AFacade
    -> BFacade
    -> CFacade
    -> DFacade
```

结构图对比如下。

错误结构：

```text
┌──────┐    ┌──────┐    ┌──────┐    ┌──────┐
│  A   │ -> │  B   │ -> │  C   │ -> │  D   │
└──┬───┘    └──────┘    └──────┘    └──┬───┘
   ^                                     │
   └─────────────────────────────────────┘
```

改造后结构：

```text
                 ┌─────────────────────┐
                 │   xbb-erp-process-xxx    │
                 │   ProcessAppService │
                 └────┬────┬────┬──────┘
                      │    │    │
                      v    v    v
                   ┌────┐┌────┐┌────┐
                   │ A  ││ B  ││ C  │
                   └────┘└────┘└────┘
                           │
                           v
                         ┌────┐
                         │ D  │
                         └────┘
```

这个改造的核心价值是：

- 流程编排被拉到独立层。
- A/B/C/D 各自只负责本域规则。
- 模块之间不再互相串联形成环。
- 后续如果流程增加审批、通知、补偿，只改 `process` 层，不污染核心模块。

#### 6. 正确处理方式三：把反向同步回调改为事件协作

有些循环依赖并不是主流程真的需要对方同步回调，而只是想在动作完成后做通知、统计、补偿、提醒。这种情况不应继续同步调用，而应改为事件。

例如错误结构：

```text
sales -> inventory -> notification -> sales
```

其中 `notification -> sales` 的真实诉求可能只是“通知模块想补充一条销售提醒记录”或“消息发送后记录一个通知状态”。这类动作通常不应该再同步打回销售模块。

错误结构图：

```text
┌───────────────┐
│ xbb-erp-module-sales │
└──────┬────────┘
       v
┌──────────────────┐
│ xbb-erp-module-inventory │
└──────┬─────────────┘
       v
┌────────────────────┐
│ xbb-erp-module-notification │
└──────┬───────────────┘
       v
┌───────────────┐
│ xbb-erp-module-sales │
└───────────────┘
```

改造后可变成：

```text
SalesOutboundAppService
    -> InventoryFacade.outbound()
    -> publish SalesOrderOutboundEvent

NotificationConsumer
    -> NotificationFacade.send()

SalesBiConsumer
    -> BiFacade.recordMetric()
```

改造后结构图：

```text
┌───────────────┐
│ xbb-erp-module-sales │
└──────┬────────┘
       │
       │ 同步调用
       v
┌──────────────────┐
│ xbb-erp-module-inventory │
└──────────────────┘

       │
       │ 发布事件
       v
┌──────────────────────────┐
│   SalesOrderOutboundEvent │
└──────┬─────────────┬──────┘
       │             │
       v             v
┌────────────────────┐   ┌───────────────┐
│ xbb-erp-module-notification │   │ xbb-erp-module-bi │
└────────────────────┘   └───────────────┘
```

这里的关键变化是：

- 主流程只完成自己必须完成的同步动作。
- 后置动作通过事件异步扩散。
- 消息、BI、预警等能力不再反向侵入销售模块主流程。

#### 7. 三种处理方式的前后变化总结

| 问题场景           | 错误结构              | 正确结构           | 适用条件         |
| ------------------ | --------------------- | ------------------ | ---------------- |
| 明确主导模块的流程 | A -> B -> C -> A      | A 统一调 B、C      | 主导方清晰       |
| 多模块长流程       | A -> B -> C -> D -> A | Process -> A/B/C/D | 无明显长期主导方 |
| 后置通知/统计/补偿 | A -> B -> C -> A      | A -> Event -> C    | 不要求强一致     |

可以把它简化理解为：

- 能收回主导模块，就不要先抽流程模块。
- 能抽流程模块，就不要让业务模块互相套娃。
- 能用事件解决后置联动，就不要同步反向回调。

#### 8. 处理循环依赖时的判断步骤

研发遇到循环调用迹象时，建议按以下顺序判断：

1. 当前流程是否存在明确主导模块。
2. 如果存在，优先把流程收回主导模块 `app.service`。
3. 如果不存在，判断是否已经是跨多个域的长流程。
4. 如果是，抽 `xbb-erp-process-*`。
5. 如果反向调用只是通知、统计、补偿类动作，改为事件。
6. 如果仍然无法拆开，重新审视模块边界，说明原模块划分可能有问题。

#### 9. 循环依赖治理的评审关注点

后续代码评审时，凡是看到下面这些信号，都应立即警惕：

- 某模块一边提供 `facade`，一边又反向依赖调用方模块。
- `app.service` 里出现越来越多“先调别人，等别人再回调我”的模式。
- 某支撑模块开始承担主业务流程状态推进。
- 新需求总是习惯在被调用模块里“顺手再调第三个模块”。
- 一个模块的测试必须依赖多个外部模块同时启动才能完成。

这些信号往往意味着：

- 结构还没彻底坏，但已经在往环依赖方向演进。

#### 10. 结论

module 间出现循环依赖时，正确处理方式不是“哪里缺逻辑就继续加一层调用”，而是优先重建流程归属。处理顺序应始终保持一致：

- 先判断主导模块能否统一编排。
- 不能统一编排时，抽 `xbb-erp-process-*`。
- 后置非强一致动作，改为事件协作。

这样才能保证：

- 模块只维护自己的领域规则。
- 流程责任有明确归属。
- 行业扩展、通知、审批、BI 等后续能力接入时，不会继续放大耦合。

### 5.1 `controller`

`controller` 只负责协议适配，不负责业务决策。其职责包括：

- 接收请求。
- 参数基础校验。
- 调用应用层。
- 返回统一响应。

禁止在 `controller` 中编写状态判断、金额计算、库存判断、跨表业务拼装逻辑。禁止 `controller` 直接注入 `mapper`。

### 5.2 `app`

`app` 是应用层，负责用例编排。其职责包括：

- 组织一个业务动作的完整执行流程。
- 定义事务边界。
- 协调多个领域对象。
- 调用其他模块的 `facade`。
- 发布领域事件或集成事件。

应用层可以跨模块调用，但只做流程组织，不负责其他模块的核心业务规则。

### 5.3 `domain`

`domain` 是领域层，是本模块最核心的业务规则所在位置。其职责包括：

- 聚合与实体状态流转。
- 业务合法性校验。
- 数量、金额、成本、账龄、信用等业务规则。
- 领域策略与领域事件。
- 仓储接口定义。

`domain` 不依赖 Spring MVC、MyBatis、Redis、HTTP Client 等技术细节。

### 5.4 `facade`

`facade` 是模块对外暴露的统一入口。其职责是：

- 提供跨模块可调用的稳定契约。
- 屏蔽模块内部实现细节。
- 避免外部模块穿透调用 `mapper` 或内部领域对象。

`facade` 不是业务规则本体，而是“模块对外服务窗口”。

### 5.5 `infrastructure`

`infrastructure` 负责技术实现，包括：

- 数据库访问。
- Repository 实现。
- 缓存访问。
- 外部系统适配。
- 消息、对象存储、远程接口调用。

它负责“怎么实现”，不负责“规则怎么决定”。

## 6. 纵向调用链规范

推荐的标准调用链如下：

```text
controller -> app.service -> domain -> repository(interface) -> infrastructure.persistence.mapper
```

跨模块调用时，必须改为：

```text
controller -> app.service -> other-module.facade -> other-module.domain -> other-module.repository
```

读写分离建议如下：

- 写链路必须走 `app -> domain -> repository`。
- 复杂列表查询、报表查询、聚合查询允许走 `app.query -> mapper` 的轻量查询通道，但只限读，不得用于写。

## 7. 横向模块隔离规范

## 7.1 基本原则

横向模块隔离遵循以下原则：

- 模块按业务职责划分，不按表划分。
- 模块拥有自己的核心数据与规则。
- 模块之间不共享内部持久化实现。
- 模块之间只通过 `facade` 协作。

## 7.2 允许的横向依赖形式

例如销售出库场景，应采用如下依赖方式：

```text
sales.app
  -> inventory.facade
  -> pricing.facade
  -> credit.facade
  -> receivable.facade
```

这属于“主导模块向多个支撑模块扇出调用”，是可接受的单向依赖。

## 7.3 禁止的横向依赖形式

以下依赖形式必须禁止：

- `sales` 直接调用 `inventory.mapper`。
- `purchase` 直接依赖 `payable` 内部实体。
- `A -> B -> C -> A` 的循环依赖。
- 把跨模块流程写进 `xbb-erp-base-common`。

## 7.4 循环调用的抽取规则

如果出现以下情况：

- A 需要调用 B。
- B 又需要调用 C。
- C 又反向调用 A。

则说明模块边界或流程编排层存在问题。推荐按以下优先级处理：

### 方式一：识别主导动作，提升到发起方 `app`

如果该业务动作存在明确主导方，例如“销售出库”显然由销售模块主导，则由 `sales.app` 完成整个流程编排，`inventory`、`receivable` 等仅提供能力。

### 方式二：抽取 `xbb-erp-process-*` 流程模块

如果该业务动作横跨多个域且不存在明显主导方，例如月结、反结账、审批通过后的多域联动，则抽取到 `xbb-erp-process-trade` 或 `xbb-erp-process-finance` 等流程模块中统一编排。

### 方式三：改同步回调为事件协作

如果某模块只是在主动作完成后做后续通知、统计、补偿、消息联动，不要求同步强一致，则改为事件驱动处理，避免形成反向同步依赖。

## 8. 公共能力在架构中的位置

用户关心的“日志、消息、审批流”等能力，不应笼统视作同一种“公共模块”，它们在架构中的位置不同：

### 8.1 技术公共能力

- 日志：位于 `xbb-erp-base-log`
- Web 框架：位于 `xbb-erp-base-web`
- 租户：位于 `xbb-erp-base-tenant`
- 持久化：位于 `xbb-erp-base-persistence`
- 缓存：位于 `xbb-erp-base-cache`

它们是通用技术能力，不包含具体业务语义。

### 8.2 业务公共能力

- 审批流：位于 `xbb-erp-module-approval`
- 消息通知：位于 `xbb-erp-module-notification`
- 价格中心：位于 `xbb-erp-module-pricing`
- 信用控制：位于 `xbb-erp-module-credit`
- 编码规则：位于 `xbb-erp-module-code-rule`
- 文件与导出：位于 `xbb-erp-module-file`
- BI 与工作台：位于 `xbb-erp-module-bi`、`xbb-erp-module-workbench`

它们虽然会被多个业务模块复用，但本质仍是业务域模块，不应下降到技术基础模块中。

## 9. 行业扩展在架构中的位置

## 9.1 行业扩展的总体定位

三个行业扩展统一位于 `xbb-erp-ext-*` 层，属于“在通用底座之上的扩展能力层”。它们不复制通用底座，而是通过扩展点增强底座能力或新增行业专属模块。

## 9.2 新增业务模块时的放置位置

如果行业扩展引入全新的业务能力，例如：

- 制造业的工单、BOM、领退补料。
- 互联网服务的里程碑、验收单。

则应作为行业扩展模块内部的独立子域实现，仍然遵循 `controller/app/domain/facade/infrastructure` 的模块结构。

## 9.3 对通用模块的增强应该放在哪里

用户特别关注的增强场景包括：

- 增加字段。
- 保存前校验。
- 保存后业务流程。

推荐规则如下。

### 9.3.1 增加字段

- 如果字段是所有行业都共用的基础属性，且会进入统一查询、统一规则、统一单据语义，则直接提升为核心模块字段。
- 如果字段只属于某个行业扩展，则优先采用“扩展表 + 扩展对象”的方式处理，例如 `purchase_order_ext_manufacture`。

行业专属字段不应轻易直接污染核心主表。只有当该字段已经演变为平台通用概念时，才允许从扩展表提升到核心表。

### 9.3.2 保存前校验

保存前校验属于业务规则增强，推荐由核心模块预留扩展接口，并由行业扩展模块实现。例如：

- `domain.extension.PreCreateValidator`
- `domain.extension.PreSubmitValidator`
- `app.extension.BeforeSaveProcessor`

行业模块提供实现，核心模块统一编排调用。禁止在核心模块代码中大量散落按行业类型判断的条件分支。

### 9.3.3 保存后业务流程

保存后的后置业务动作，如果需要强一致，应通过核心模块 `app` 层预留扩展后处理器或领域事件联动；如果不需要强一致，则通过事件方式交由行业模块异步处理。

推荐扩展点包括：

- `app.extension.AfterSaveProcessor`
- `domain.event.*`
- `app.extension.AfterApproveProcessor`

原则上，核心模块负责在稳定扩展点上触发，行业模块负责实现增强逻辑。

## 10. 移动端入口在架构中的位置

移动端入口位于 `xbb-erp-app-mobile`。它不是单独的一套业务模型，而是通道级装配层。

移动端接口的特点包括：

- 面向待办审批、轻量查询、消息处理、简化表单。
- 返回数据结构通常更偏向聚合视图或移动端友好格式。
- 可以复用与后台一致的 `app`、`domain`、`facade` 和数据库。
- 不应复制一套业务规则。

推荐在业务模块中为移动端提供 `controller.mobile` 适配层，由 `MobileApplication` 按需扫描装配。

## 11. 推荐的项目工程架构图说明

项目工程架构图的解读方式如下：

- 最上层是三个访问与执行入口：后台、移动端、任务执行。
- 中间的 `controller`、`app`、`domain`、`infrastructure` 是每个业务模块的纵向模板。
- 横向业务模块按基础主数据、交易执行、财务协同、平台能力四层组织。
- 流程编排模块位于业务模块之上，用于消除横向环依赖。
- 行业扩展位于业务模块侧边，表示“增强”而非“复制”。
- 最底层是技术底座模块，所有业务模块统一依赖。

工程架构图文件见：

- `11A-进销存系统项目工程架构图.mmd`

## 12. 推荐的依赖关系图说明

依赖关系图的解读方式如下：

- 最底层为技术底座，被上层所有业务模块依赖。
- 组织、主数据、商品、合同、资金账户等是平台共用核心底座。
- 采购、销售、库存为交易主链。
- 应收、应付、收付款、发票、对账、结账为财务协同主链。
- 价格、信用、审批、通知等平台能力为多个业务模块提供横向支撑。
- 流程编排模块依赖多个业务模块，但业务模块不能反向依赖流程模块。
- 行业扩展依赖核心模块预留的扩展点，但核心模块不能编译期依赖行业模块。

## 13. 后续更新迭代必须遵守的规范

以下规范应作为后续更新迭代的强约束：

### 13.1 模块边界规范

- 不允许跨模块直接调用 `mapper`。
- 不允许跨模块直接依赖对方持久化对象或内部领域服务。
- 跨模块只能依赖对方 `facade` 契约。

### 13.2 分层落点规范

- `controller` 只做协议适配。
- `app` 只做用例编排与事务边界控制。
- `domain` 只做业务规则与状态语义。
- `infrastructure` 只做技术实现。

### 13.3 流程抽取规范

- 一个业务动作存在明确主导模块时，由主导模块 `app` 编排。
- 多模块共同构成的长流程，应抽取到 `xbb-erp-process-*`。
- 非强一致后置动作，应优先改为事件协作。

### 13.4 行业扩展规范

- 新行业能力优先落在 `xbb-erp-ext-*`。
- 对核心模块的增强必须基于扩展点。
- 禁止核心模块大量出现行业分支条件逻辑。
- 行业专属字段优先放扩展表，不直接污染通用主表。

### 13.5 启动装配规范

- 启动类只承担装配职责，不承载业务逻辑。
- 新入口的增加，优先通过新 app 装配模块完成，不直接污染既有业务模块。
- 移动端控制器与后台控制器分包管理，不混放。

### 13.6 依赖方向规范

- 技术底座不依赖业务模块。
- 核心业务模块不依赖行业扩展模块。
- 行业扩展模块依赖核心模块扩展点。
- 业务模块之间尽量保持单向依赖。
- 出现编译期环依赖时，必须中止开发并先完成结构重构。

## 14. 结论

进销存系统的工程结构不能只停留在“按 controller/service/mapper 三层拆包”的层面，而必须从顶层 module 结构、纵向调用链、横向协作边界、行业增强机制和启动装配策略五个维度同时定义。只有这样，系统才能在 P0 快速起步的同时，避免后续因为模块耦合失控、行业逻辑污染核心底座、流程编排无序和依赖环扩散而导致整体架构失稳。

本文档给出的方案本质上是一套“以通用底座为核心，以流程编排消除环依赖，以扩展点承接行业增强”的工程架构约束，后续所有功能新增、模块新增和行业增强都应在这套结构下进行。

# 业务模块目录规范

## 适用范围与事实来源

本规范以 `xbb-erp-module-customer` 的当前稳定结构为基准，适用于所有 `xbb-erp-module-*` 业务模块，但不适用于 `xbb-erp-module-common` 和 `xbb-erp-module-org`。它定义目录职责与依赖边界，不把客户字段、状态或具体业务规则复制给其他领域。

目录职责以本文件为唯一说明源；跨模块开发流程以 `DDD业务模块开发指南.md` 为准，强制工程规则以 `../harness/工程规则唯一事实源.md` 为准。新业务模块先按本规范建最小目录，再按实际用例按需扩展。

## 目录总览

```text
xbb-erp-module-<domain>/
  src/main/java/xbb/ai/erp/module/<domain>/
    admin/
    application/
    domain/
    infrastructure/persistence/
  src/main/resources/mapper/<domain>/
  src/test/java/xbb/ai/erp/module/<domain>/
  src/test/resources/
```

- 目录按职责存在，不为对齐骨架创建空目录；没有草稿、动态列表或外部端口时，可不创建对应子目录。
- 依赖方向固定为 `admin -> application -> domain`；`infrastructure` 实现 `domain` 或 `application.port` 的接口。`domain` 不依赖 HTTP、Spring Web、ORM、PO、DTO、VO。
- 同一类职责不得因方便而跨层落位；无法归类时，先确定它属于协议、用例、领域语义或技术实现，再决定目录。

## 生产代码目录

| 目录 | 应放文件 | 不应放文件 |
| --- | --- | --- |
| `<domain>.admin` | `*AdminController`、仅 HTTP 可见的业务枚举和协议常量 | AppService 编排、Mapper、PO、领域规则 |
| `<domain>.admin.dto` | 请求 `*DTO`、主档/子档入参、查询和草稿入参 | VO、PO、领域查询对象 |
| `<domain>.admin.vo` | 响应 `*VO`、列表行、详情、表单初始化、草稿返回 | DTO、PO、Repository 查询结果 |
| `<domain>.application.assembler` | DTO/VO、领域模型、应用 Pojo 之间的单向转换 | Mapper 调用、事务、HTTP 响应包装 |
| `<domain>.application.config` | 字段规则、应用服务等 Spring 装配配置 | Controller、领域规则、SQL |
| `<domain>.application.field` | 页面场景字段工厂、字段元数据、字段规则 | 领域持久化与业务主数据 |
| `<domain>.application.pojo` | 保存上下文、分区状态、扩展数据等应用层内部对象 | HTTP DTO/VO、PO |
| `<domain>.application.port` | 非领域表或外部能力的应用端口，例如草稿仓储 | Redis/MyBatis/HTTP 客户端实现 |
| `<domain>.application.provider` | 向公共能力提供元数据的 Provider，例如 `*ListMetaProvider` | 业务列表数据查询、SQL |
| `<domain>.application.schema` | 页面筛选协议到领域查询条件的适配、属性/操作符白名单 | 前端传入 SQL、Mapper XML |
| `<domain>.application.service` | 应用服务接口和薄总入口接口 | 具体 SQL、Controller 参数解析 |
| `<domain>.application.service.impl` | 薄总入口实现，只负责分派到具体用例服务 | 堆积查询、保存、草稿和删除全部细节 |
| `<domain>.application.service.query` | 列表、详情、新建/编辑表单初始化等查询用例 | 正式保存、删除、草稿写入 |
| `<domain>.application.service.save` | 提交保存、主子档同步、事务边界 | HTTP 协议解析、Mapper 直连 |
| `<domain>.application.service.draft` | 草稿保存、草稿列表和草稿加载用例 | 正式领域表持久化实现 |
| `<domain>.application.service.delete` | 删除用例、引用检查和子档删除编排 | 列表查询、表单初始化 |
| `<domain>.application.validator` | 协议、通用字段、业务三类校验器及字段校验规则 | HTTP 响应、持久化实现 |
| `<domain>.domain.config` | 不依赖基础设施的纯领域配置；通常按需创建 | Spring MVC、ORM 或 Bean 装配 |
| `<domain>.domain.field` | 纯领域字段规则；通常按需创建 | 页面字段元数据、前端展示规则 |
| `<domain>.domain.model` | 聚合根、实体、值对象等领域模型 | PO、DTO、VO、MyBatis 注解 |
| `<domain>.domain.pojo` | Repository 查询条件和领域内部传递对象 | 页面字段元数据、HTTP 对象 |
| `<domain>.domain.repository` | 领域读写接口及领域所需读模型契约 | MyBatis-Plus 或 Redis 实现 |
| `<domain>.infrastructure.persistence.convertor` | 领域模型与 PO 的转换 | Controller 入参与 VO 转换 |
| `<domain>.infrastructure.persistence.mapper` | MyBatis-Plus `*Mapper` 接口 | 业务校验、事务、VO 组装 |
| `<domain>.infrastructure.persistence.po` | 与表映射的 `*PO`，继承 `BaseEntity` | DTO、VO、`Boolean` 数据库字段、重复基础字段 |
| `<domain>.infrastructure.persistence.repository` | Domain Repository 和 Application Port 的 MyBatis/Redis 实现、查询条件落地 | HTTP 返回对象、Controller、领域规则 |
| `src/main/resources/mapper/<domain>` | Mapper 对应的 `*Mapper.xml` 专用 SQL | Java 业务逻辑、跨模块 XML |

`application.service.draft`、`application.port` 和其基础设施实现应成对出现；草稿不是领域表时，端口定义放在 Application，而不是强行放入 Domain Repository。动态列表能力涉及 `provider` 与 `schema` 时，两者必须共同存在：前者提供页面元数据，后者实施服务端筛选白名单。

## 命名与落位补充

- HTTP 入参使用 `*DTO`，非脚本接口继承 `BaseDTO`；HTTP 出参使用 `*VO`；应用和领域内部中转使用 `*Pojo`。
- 数据库对象使用 `*PO`，枚举使用 `*Enum`；`*PO` 必须继承 `xbb.ai.erp.base.persistence.entity.BaseEntity`，不得重复声明基础字段。
- `Controller` 仅调用 Application 服务并包装 `ResultVO.success()`；所有数据库访问经 Repository，禁止 `Controller` 或 Application 直接注入 Mapper。
- 列表子档摘要必须批量查询；保存主档与子档由 `application.service.save` 在明确事务边界内编排。

## 测试与资源目录

| 目录 | 应放内容 |
| --- | --- |
| `src/test/java/.../<domain>/admin` | Controller、DTO/VO 契约和 HTTP 边界测试 |
| `src/test/java/.../<domain>/application/...` | Field、Provider、Port、Query/Save/Draft/Delete 用例测试；包结构按被测生产代码镜像 |
| `src/test/java/.../<domain>/domain/...` | 领域模型、领域字段规则和 Repository 契约测试 |
| `src/test/java/.../<domain>/infrastructure/persistence/convertor` | Model/PO 转换测试 |
| `src/test/java/.../<domain>/infrastructure/persistence/repository` | Repository 实现单元测试 |
| `src/test/java/.../<domain>/infrastructure/persistence/integration` | MySQL、Redis、Flyway 等真实基础设施集成测试 |
| `src/test/java/.../<domain>/sql` | SQL、迁移或 Mapper 行为的专项测试 |
| `src/test/resources/fixtures` | 测试固定数据、导入样例和专用 SQL 资源 |
| `src/test/resources/mockito-extensions` | 测试框架扩展配置；无需要不创建 |

测试目录以生产代码职责为镜像，而不是按测试人员或需求名称分组。新生产 package 只要包含可观察逻辑，就应评估并在对应测试镜像下补充测试；纯标记包或无逻辑配置可在交付记录说明不新增测试的原因。

## 新 package 登记规则

任何适用范围内的 `xbb-erp-module-*` 新增生产 package，必须在同一变更中更新本文件，记录新目录的职责；不得只在代码中出现新的目录结构。

登记步骤：

1. 判断该 package 是否属于既有目录职责。若是，只在该目录已有说明下补充必要边界；若否，新增一行“目录 / 应放文件 / 不应放文件”。
2. 写明它依赖的上游层和允许依赖的下游层，避免形成新的反向依赖。
3. 判断是否需要对应测试目录、资源目录、API 文档、模块地图或数据库说明，并在同一任务中回写。
4. 新目录若成为跨模块稳定模式，再将其上升到 `DDD业务模块开发指南.md`；仅某模块需要时，不把它提升为通用强制目录。

新增 package 的最小登记格式：

```md
| `<domain>.application.example` | 某类用例专属的…… | Controller、PO、Mapper |
```

目录是客户模块暂有但不应普遍复制的，必须在本业务模块自己的 `docs/modules/<domain>/` 中说明原因；不改变本规范的基准结构。

## Agent 与 Harness 使用

- 新增或扩展业务模块前，先读取本规范、`DDD业务模块开发指南.md`、目标模块代码、模块地图和相关 API 原子文档。
- 新增 package 时，检查本规范是否已覆盖；未覆盖即先更新本文件，再提交代码目录变更。
- `scripts/harness-verify.sh` 检查本规范文件存在；目录职责和登记内容由代码评审与模块交付检查共同确认。

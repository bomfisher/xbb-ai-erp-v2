# 后端文档规范

## 目标与原则

本文定义后端文档的分类、事实源、存放位置与维护边界。目标是让人和 Agent 先通过地图定位最小必要上下文，再读取对应事实源；不以复制正文解决检索问题。

- 一个事实只保留一个完整事实源；其他文档只写摘要和链接。
- 规则、接口、数据库、业务语义与交付证据分别维护，避免同一信息在多处漂移。
- 新文档先判断它回答的问题，再选择目录；不能仅按“写文档的人”或一次需求名称归档。
- 存量文档渐进迁移，除非当前任务涉及该文档，不因目录调整批量移动或重写。

## 分类与存放

| 类型 | 回答的问题 | 完整事实源 | 存放位置 | 维护时机 |
| --- | --- | --- | --- | --- |
| 工程规则 | 所有后端开发必须遵守什么 | 本文与 `工程规则唯一事实源.md` | `docs/harness/` | 规则变更 |
| 交付流程与验证 | 如何交付、如何验证、如何发布 | 对应 Harness 文档 | `docs/harness/` | 流程或门禁变更 |
| 项目与模块地图 | 代码和文档在哪里、谁负责什么 | `项目业务module导航.md`、`文档地图.md` | `docs/base/`、`docs/harness/` | 新模块、边界变化 |
| 后端通用规范 | DDD、持久化、列表/表单、保存等跨模块实现方式 | 对应指南 | `docs/guide/` | 跨模块稳定约定变更 |
| 通用功能文档 | 可被多个领域直接复用的能力如何接入 | 功能指导文档 | `docs/guide/common/<能力>/`（新增） | 能力新增或契约变更 |
| 业务通用文档 | 多个业务领域共享的业务概念、状态或流程 | 领域说明文档 | `docs/guide/business/<主题>/`（新增） | 业务共识变更 |
| 业务个性化文档 | 某领域特有的术语、规则、状态机、集成边界 | 模块领域文档 | `docs/modules/<domain>/`（新增） | 模块功能变化 |
| 独立功能文档 | 独立交付能力的目标、范围、方案与验收 | 功能说明/设计文档 | `docs/features/<feature>/`（新增） | 非微小功能立项与交付 |
| API 原子文档 | 一个 HTTP 接口的完整请求、响应、错误和兼容事实 | 单接口文档 | `docs/api/endpoints/` | 接口契约变化 |
| API 聚合与导航 | 某业务或功能有哪些接口、如何跳转 | `docs/kn/*.md`、`docs/kn/总目录.md` | `docs/kn/` | API 原子文档变化 |
| 数据库设计说明 | 表、字段和业务数据意图 | 可读 SQL 说明 | `docs/sql/` | 表结构变化 |
| 数据库执行事实 | 环境实际应执行什么迁移 | Flyway 迁移 | `xbb-erp-app-admin/src/main/resources/db/migration/` | 结构变化 |
| 决策记录 | 为什么采用某个长期且难逆转的方案 | ADR | `docs/adr/`（新增） | 架构或关键业务决策 |
| 交付记录 | 一次需求如何实施、验证结果和遗留项 | 交付报告 | `docs/records/delivery/`（新增） | 功能交付完成 |
| 历史方案与计划 | 已完成或失效方案的追溯依据 | 历史文档本身 | `docs/superpowers/`（存量） | 仅在追溯时读取 |

`docs/kn` 不是业务规则或接口字段的完整事实源：`*-m.md` 是业务聚合，`*-s.md` 是功能聚合，均只维护摘要、差异与链接。存量 `docs/api/*.md` 可继续作为兼容索引或历史材料；新增完整接口事实统一写入 `docs/api/endpoints/`。

## 新目录的最小模板

新增目录按需创建，不为预留而创建空目录。

```text
docs/modules/<domain>/
  README.md                 # 模块边界、术语、关联 API/代码入口
  domain-rules.md           # 特有规则、状态机、边界和异常语义
  integrations.md           # 外部/跨模块依赖；没有则不建

docs/features/<feature>/
  README.md                 # 目标、范围、验收、关联模块
  design.md                 # 仅在存在设计取舍时创建
  rollout.md                # 迁移、灰度或回滚要求；没有则不建

docs/guide/common/<capability>/
  README.md                 # 适用范围、接入步骤、限制、示例链接
```

目录名用英文 kebab-case；文件名优先使用稳定中文业务名或英文能力名，同一目录内保持一致。文档开头必须说明“适用范围、事实来源、关联入口”；废弃文档写明替代文档和废弃日期，不静默删除仍可能被引用的规范。

## 事实源与引用规则

1. 工程规则以 `docs/harness/工程规则唯一事实源.md` 为准；`AGENTS.md` 只保存读取入口、协作约束和不可省略的短规则。
2. 单接口字段、示例、错误码和兼容策略以 `docs/api/endpoints/<domain>-<action>.md` 为准；业务/功能聚合只链接。
3. 表结构的执行事实以 Flyway 为准，`docs/sql/` 说明“为什么”和可读设计，不替代迁移。
4. 跨模块稳定实现方式写入 `docs/guide/`；仅某模块成立的规则写入 `docs/modules/<domain>/`，不能反向污染通用指南。
5. 设计方案不是永久规则。方案落地后，将稳定结论回写到规则、指南、模块文档或 API 文档，并在方案中链接最终事实源。

## 文档地图与按需加载

`docs/harness/文档地图.md` 是文档定位入口，按“任务类型 → 必读文档 → 可选文档 → 代码入口”组织。Agent 与开发者遵循：

1. 先读取根 `AGENTS.md`、Harness `README.md`、工程规则和文档地图。
2. 根据任务类型在地图中选择最小必读集；先读事实源，再读聚合或历史材料。
3. 只有任务涉及某模块、接口、数据库、跨模块能力或历史决策时，才加载其对应文档。
4. API 契约变化执行 `.claude/commands/multi-player/SKILL.md`，同步原子文档、聚合文档和 `docs/kn/总目录.md`。
5. 新增模块、通用能力、独立功能或 ADR 后，回写文档地图的对应索引；不在 `AGENTS.md` 堆叠长清单。

## 维护责任

- 改工程规则：同步 `工程规则唯一事实源.md`、本规范和受影响的 SKILL/校验脚本。
- 改模块边界：同步模块地图、模块文档和相关独立功能文档。
- 改通用能力：同步通用功能指导、引用它的业务个性化文档和测试说明。
- 改接口：先更新 API 原子文档，再更新业务/功能聚合与双入口导航。
- 改数据结构：新增 Flyway、更新可读 SQL 设计、模块文档和受影响 API。
- 完成交付：将稳定结论回写事实源；仅把过程、证据和待办保留在交付记录。

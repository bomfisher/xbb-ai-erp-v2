## 经验总结
- ai生成中大型项目首先完成以下事情
  - 确定技术框架，写到rule
  - 确定后端项目结构，至少是核心项目结构
    - 底层的 config、common、log等
    - 顶层的启动包
    - 中间业务包留1到2个用来做验证
  - 一个合适的持久层生成工具，用于快速生成基础controller到mapper
  - ai生成前端项目框架
- 把当前每个包的职责写到rule
- 开始搭建公共底层
  - 优先完成菜单
  - 对接列表
    - 列表页的列表数据、列表表头、筛选项、头部按钮、底部按钮、分页逻辑需要先定义好规范，再去接入前端。
      - 不然会出现扩展困难，不同模块实现方式不同等问题
  - 对接新建页、编辑页
    - 如果未来想要开放字段能力设置的，新建、编辑页的字段维护建议和列表表头方案一并考虑
  


## 零散经验
- 逆向工程很重要
  - 省token
  - 节约时间
  - 提高AI效率
- 做具体的功能时，可以直接在项目中，手动写一下部分实现代码，或者是方法占位，可以帮助AI理解
- 早期业务只做CRUD，等模块完整，在做模块之间或与基础能力之间的对接
- 前端代码生成完，一定要用ai review一遍，实现列表时，明确要求抽取公共组件，但是AI没有招办

## 禁止项
- 早期不要把完整的业务模块设计文档喂给ai，除非是非常小，没有周边耦合的业务
  - 这个时候项目要啥没啥，不足以支持一个业务模块


## 扩展
- 主维度用业务维度：比如 客户 一份总文档，下面按 列表 / 新建 / 编辑 / 详情 / 删除 分组；因为人和 AI 在做需求、排查问题时，通常先想到“客户业务”
- 次维度用功能维度索引：再维护一份轻量索引，比如“所有列表页接口清单”，里面只放 业务名 + 完整路径 + 用途 + 跳转到主文档
- 不要双份正文：同一个 列表接口 的请求示例、响应示例、业务规则，只在“客户主文档”里维护；功能索引里只做引用导航
- 完整路径要保留：尤其在功能索引里必须写全，比如 /erp/v1/customer/list，这样 AI 扫一眼就能唯一定位，不会把不同业务的 list 混掉
- 最适合 AI 的结构是：业务主文档 负责语义完整，功能索引 负责快速检索；这比“纯按功能”或“纯按业务但没有横向索引”都更稳


文档提供的是代码里分散、AI一次读不全或不容易归纳的上下文，比如“这个列表页的6个接口分别负责什么、调用顺序、关键筛选字段、哪些字段只是展示哪些字段参与查询”；如果文档只是把代码逐段重述，通常不如 AI 直接读代码。
对 AI 最提效的格式不是长篇说明，而是结构化短文档：先写页面目标和主流程，再给一张接口表（用途、HTTP 方法、完整路径、入参 DTO、关键返回字段、调用时机/依赖关系），最后补 3~5 条业务规则或坑点。
你这个“列表页 6 个接口”的场景里，建议把完整接口路径写出来，至少在接口总表里必须有；正文里不必反复重复，但首次出现或容易混淆时要写全，否则 AI 很容易把相似接口、不同 module 的接口、旧版/新版路径混在一起。
